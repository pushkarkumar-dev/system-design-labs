Build a B+Tree from scratch — the data structure inside every SQL database and many NoSQL engines. Go from in-memory node splits to a page-managed on-disk tree with WAL durability.
Production B+Trees use the B-link variant where each node holds a right-sibling pointer and a high-key. This allows concurrent reads and writes to different paths without global locks — our implementation uses a Mutex around the whole tree.
Real databases use a buffer pool with a sophisticated replacement policy (LRU-K, CLOCK). Our LRU page cache is correct but doesn't handle dirty-page write-back correctly under memory pressure.
B+Trees in real databases (InnoDB, PostgreSQL) store multiple versions of each row for snapshot reads. Our tree stores only the latest value — no time-travel queries, no REPEATABLE READ isolation.
We split nodes on overflow but don't merge on underflow. Real B+Trees merge or redistribute when a node drops below 50% full — otherwise repeated deletes leave a sparse tree that wastes pages.

Building a B+Tree by inserting one key at a time from sorted input is inefficient. Real systems bulk-load: write leaves left-to-right, then build internal levels bottom-up. 10x faster for initial construction.
Build a bytecode VM from scratch — stack machine, closures with upvalues, and tail call optimization. Then read the same code's JVM bytecode with javap and see exactly how Java's VM handles closures, lambdas, and why it deliberately skips TCO.
Lua 5 switched from stack to register VM for a 2x speedup. Register VMs have more complex instructions but fewer of them — fewer dispatch cycles per high-level operation. V8's Ignition bytecode is register-based.
Our VM interprets bytecode. The JVM's JIT (C1/C2) compiles hot bytecode to native machine code after profiling. First execution is slow (interpreted), repeated execution is fast (compiled). We have no JIT — every instruction pays dispatch overhead forever.
Our VM leaks memory — closures and strings are never freed. A real VM needs a GC to reclaim unused Values. The GC's interaction with the call stack (rooting all live values to prevent collection) is the hard part. Our Rc does reference counting, not tracing GC.
Our dispatch loop uses a match statement — the CPU branch predictor can't predict which instruction comes next. Computed goto (GCC extension, available in unsafe Rust via function pointers) jumps directly to each handler, eliminating the branch. CPython 3.12 uses this for ~15% speedup.
We have no objects, structs, or prototype chains. A real VM needs a way to represent structured data with field access and method dispatch. The JVM uses the classfile constant pool and vtable for this. Our VM has no concept of a type beyond Int, Bool, Str, and Closure.
Our VM has no exception mechanism. Real VMs use exception tables: a mapping from [ip_start, ip_end] to handler_ip. On exception, the VM scans the table for a matching handler, unwinds frames, and jumps to the handler. We would need to add THROW and TRY/CATCH instructions.

Models larger than 70B params don't fit on one GPU. Tensor parallelism shards the weight matrices across GPUs — each GPU computes a slice of the attention heads and reduces via AllReduce collectives. Our single-process implementation cannot scale beyond what fits in one device's memory.
A small draft model generates N tokens speculatively; the large model verifies all N in one forward pass. Accepted tokens are free — rejected ones cost one draft plus one verify pass. This achieves 2-4x throughput at the same output quality with no model changes.
FP32 weights are 4 bytes; INT4 is 0.5 bytes — an 8x reduction. Quantized inference requires dequantizing weights on the fly per layer, introducing additional memory reads. GPTQ and AWQ are the standard post-training quantization algorithms. Our implementation uses FP32 throughout.
System prompts (thousands of tokens) are the same across all requests in a session. vLLM caches the KV state of the prefix — new requests with the same prefix skip recomputation entirely. Our paged attention is a prerequisite for prefix caching, but we don't implement the cache lookup.
Production APIs stream tokens to clients as they are generated (SSE or chunked HTTP). This requires a generator protocol, per-request callbacks, and backpressure when the client reads slower than the model generates. Our server returns the full generated text only after completion.

Build all three logical clocks: Lamport (causal ordering), vector clocks (concurrency detection), and HLC (real time plus monotonicity). Port to Java to show the algorithms are language-agnostic building blocks for any distributed system.
Vector clocks grow with the number of nodes — N nodes means an N-element vector per event. Interval Tree Clocks (ITC) encode clock state compactly for dynamic systems where nodes join and leave frequently. Forking a clock creates two non-overlapping intervals; joining merges them. This is O(1) space per node regardless of total cluster size.
Used in Riak. Solves the sibling explosion problem in vector clocks where concurrent updates keep accumulating separate versions. DVVs bound the number of concurrent versions by collapsing confirmed causal history into a single dot per replica, discarding versions that are dominated by the causal past.
TrueTime uses GPS receivers and atomic clocks to give bounded uncertainty intervals [earliest, latest] for the current time. Spanner commits a transaction only when the uncertainty interval is guaranteed to not overlap with any future transaction. Our HLC approximates this but cannot give hard guarantees on the uncertainty bound.
In a distributed database, two transactions that appear concurrent by HLC might actually be causal if the clock skew falls within the uncertainty window. Handling this correctly requires either TrueTime-style commit wait (pause until uncertainty clears) or a global sequencer service. HLC alone is not sufficient for strict serializability.
Our vector clock is a full map per event. For N=100 nodes, each event carries 100 uint64 values — 800 bytes of metadata per event. Production systems use bloom filters, summary structures, or plum-tree gossip to reduce this overhead. The O(N) message overhead is why vector clocks are rarely used verbatim in large clusters.
Version vectors track versions of replicated objects (how many writes each replica has seen). Vector clocks track event causality. They look syntactically identical but mean different things — a version vector answer to 'has replica A seen replica B's writes?' while a vector clock answers 'did event A happen before event B?'. Confusing them is a famous distributed systems bug documented by Riak engineers.

Build a Log-Structured Merge-Tree KV store in four stages: memtable, SSTable flush, size-tiered compaction with bloom filters, and an L-shaped compaction strategy. Wire it into Spring Boot via RestClient.
We implement size-tiered (Cassandra-style). Level compaction bounds the number of SSTables per level, dramatically reducing read amplification at the cost of higher write amplification. RocksDB's default: 7 levels, 10:1 ratio. The choice between them is the central tuning decision in any LSM deployment.
Our memtable is not crash-safe without a WAL. If the process dies before a flush, in-memory puts are lost. Real LSM stores (RocksDB, LevelDB, Cassandra) use a WAL + memtable together. The previous lab is exactly the WAL you'd pair with this memtable.

We write raw bytes. Production SSTables compress each block with Snappy or Zstd before writing. At 4:1 compression ratio, a 4 MB flush becomes a 1 MB SSTable — 4× more data fits in the same disk I/O budget.
RocksDB's way of having separate LSM trees with independent memtable sizes, compaction strategies, and block cache pools. Column families let you tune the LSM for different workloads in the same process — e.g., a fast-write CF for events and a read-optimized CF for metadata.

Lookahead decoding generates draft tokens from earlier positions in parallel without a separate draft model — using the Jacobi iteration approach. This requires no draft model but achieves lower acceptance rates than a trained draft.
Standard speculative decoding produces exactly the same output distribution as target-only decoding (provably). But tree speculative decoding can introduce distribution shift if the acceptance criterion is not carefully derived.
vLLM implements speculative decoding with paged attention — draft tokens must be allocated in pages that may be freed on rejection. Integrating with page management requires significant engineering.
Build a stream processor from tumbling window aggregation to sliding windows with watermarks to exactly-once delivery via two-phase commit — making Flink's design choices concrete.
Our processor is single-node. Flink and Kafka Streams partition state by key across workers. Redistributing state during rebalancing requires a state migration protocol.
Session windows group events that occur within a gap timeout of each other — no fixed size. Merging two sessions when new events connect previously disjoint gaps requires tracking session boundaries per key.
Beam/Flink's global window + trigger model is more expressive than tumbling/sliding. Triggers fire on element count, data arrival, or periodic timer — mixing time and count is complex.
Flink uses RocksDB as a state backend for aggregations that don't fit in memory. Our in-memory maps explode for high-cardinality keys over long windows.
Kafka Streams achieves exactly-once via Kafka's transactional producer — producing output and committing offsets in the same transaction. This works because Kafka is both source and sink. Our 2PC requires a separate checkpoint store.
When the sink is slow, backpressure should propagate upstream to slow the source. Our buffered channels provide local backpressure, but coordinating across network-connected operators requires credit-based flow control.
Build a userspace TCP/IP stack in C using a Linux TUN device: parse IP/TCP headers, implement the 3-way handshake state machine, add reliable delivery with retransmission, then slow start and congestion avoidance — understanding what happens below every socket() call.
The kernel uses sendfile() and DMA scatter-gather; every TUN read/write crosses the kernel-user boundary copying the full packet.
Real stacks hold connections in TIME_WAIT for 2MSL (up to 4 minutes) to handle delayed duplicates; our table has MAX_CONNS=64 slots total.
CUBIC uses a cubic function of time since last congestion event; BBR models bottleneck bandwidth and RTT. Both significantly outperform Reno in high-BDP paths.
Packets larger than the path MTU get fragmented; our stack drops anything that arrives in fragments.
SACK, window scaling (beyond 64KB), timestamps, and TCP Fast Open are all absent — each adds protocol complexity and parser surface area.
SYN flood resistance (SYN cookies), blind reset attacks (RFC 5961 sequence number checks), and TLS integration are not implemented.
Build a time-series database from scratch — from naive float storage to Gorilla-style 12:1 compression. Then wire it into Spring Boot as a Micrometer registry so any JVM app can push metrics into it automatically.
We write compressed chunks to disk directly. A crash mid-chunk loses the current block. Production TSDBs (Prometheus, InfluxDB) use a WAL for the current chunk's raw data.
We assume timestamps arrive in order. Real systems have clock skew, network delays, and out-of-order batches. Handling late data requires an in-memory buffer window (e.g., 2 minutes) before flushing.
One file per metric breaks down at high cardinality (millions of unique label combinations). Prometheus uses an inverted index over label sets; our flat metric-name approach doesn't scale to dynamic labels.
Percentile queries (p99 latency) require approximation algorithms (t-digest, DDSketch). Storing raw values and computing exact percentiles is too expensive at scale.
Production monitoring uses remote_write protocol (Prometheus) to forward metrics to long-term storage (Thanos, Cortex, Mimir). Our TSDB is single-node only.
Our chunks are closed by size (128 points). Production TSDBs align chunks to time boundaries (2-hour blocks in Prometheus) so time-range queries map cleanly to chunk files — no need to scan partial chunks.
Build a BPE tokenizer from scratch — character-level baseline to GPT-2 style byte-level BPE. Understand why 'don't' tokenizes as [don, 't] and how the vocabulary tradeoff between compression ratio and model performance works.
BPE is greedy and produces a fixed vocabulary after training. Unigram LM (used by T5, LLaMA) trains a probabilistic model and prunes tokens by likelihood — it can produce multiple valid tokenizations and pick the most probable one. More principled but harder to implement.
Raw text has many Unicode forms of the same character (e.g., 'n' with combining tilde can be one codepoint or two). Without normalization, the same word gets different tokens. Our tokenizer skips normalization.
Production tokenizers reserve special tokens for model training signals. These have their own IDs and are never merged. Adding them retroactively breaks all existing encoded sequences.
BPE training is O(N x V) where N is corpus size and V is vocab size. For GPT-4's 100k vocabulary on a 1TB corpus, this takes hours on CPU. Production trainers use C extensions (HuggingFace tokenizers uses Rust) for ~100x speedup.
Our Python implementation uses a Counter to find the most frequent pair — O(N) per merge step. With a priority queue and incremental updates, it can be O(N log V). The HuggingFace Rust tokenizer uses this optimization.
GPT-2's byte-level BPE never produces UNK — any Unicode character falls back to its constituent bytes (always in vocabulary). Our v0 uses UNK, which causes information loss for rare scripts.
Build a GPT-style transformer from scratch in PyTorch — from scaled dot-product attention to a trained character-level model on TinyShakespeare. Expose it via a FastAPI inference server and consume it from Spring AI's ChatClient, which treats our toy model identically to GPT-4.
Our attention is O(n²) in memory. Flash Attention rewrites the attention kernel to avoid materializing the full attention matrix — 10-100× memory savings, essential for long contexts.
Inference recomputes K/V for every token. KV cache saves prior K/V tensors; each new token only needs to attend to cached K/V. Required for practical inference speed.
We use sinusoidal PE. Modern LLMs (LLaMA, GPT-NeoX) use RoPE — applied at attention, extends to longer contexts than training.
Grouped-query attention (LLaMA 3) shares K/V across query heads, reducing KV cache size by 4-8×. Our MHA has separate K/V per head.
We use character-level tokenization. Real LLMs use Byte-Pair Encoding with vocab size ~50k. See the BPE Tokenizer lab.
We train in float32. bf16/fp16 with gradient scaling gives 2× speedup. Essential for large models but tricky to implement correctly.
Build a vector similarity index from brute-force flat scan to HNSW graph search to IVF-PQ with 32x compression — then plug it into Spring AI as a VectorStore.
Production implementations (Faiss, hnswlib) use AVX-512 SIMD to compute 16 float dot products per instruction. Our scalar loop is 8–16× slower on modern CPUs.
HNSW graphs must be serialized to disk and memory-mapped for production use. The graph structure (adjacency lists) requires careful layout for cache locality.
Real use cases need filtered ANN: find top-10 similar embeddings where user_id = 42 AND created_at is recent. Pre-filtering vs post-filtering have very different recall characteristics.
Billions of vectors require sharding across machines. Weaviate, Pinecone, and Qdrant handle shard routing, replication, and rebalancing as the corpus grows.
HNSW supports efficient insertion but deletion requires marking nodes as deleted (tombstones) and periodic compaction. IVF requires rebuilding centroids on significant data drift.
Our 256-centroid PQ is fixed. Production systems tune the number of subspaces and codebook size per dataset, and support scalar quantization (INT8) and binary quantization as alternatives.
Build a streaming voice assistant in Python: Whisper STT with energy-based VAD, conversation history LLM, sentence-level TTS chunking — first audio chunk in 520ms on a consumer laptop.
GPT-4o voice and Moshi operate directly on audio tokens without a separate STT/TTS boundary; our pipeline introduces 290ms + 140ms of discrete stage latency.

Multi-speaker scenarios require diarization (pyannote.audio) to assign transcript segments to speakers; our VAD treats all speech as one speaker.
When the assistant is speaking and the user interrupts, the microphone picks up the speaker output; AEC is required for barge-in support.
Production TTS systems (ElevenLabs, Kokoro) support style, emotion, and prosody tags; pyttsx3 exposes only rate and volume.

Build an append-only Write-Ahead Log in three built stages (in-memory core, file-backed with fsync, group commit (35× throughput gain)) and a designed fourth (segment rotation). Then wire it into a Spring Boot service with RestClient and Caffeine caching.
v3 describes rotation but is not built yet. Even with it, real WALs track which segments have been checkpointed and can be deleted without breaking replication.
Our WAL grows forever. RocksDB compacts SSTs while the WAL is still running; the coordination (manifest files, column-family checkpoints) is non-trivial.
Raft's log replication is essentially a distributed WAL. Leader tracks each follower's nextIndex separately; our WAL has no concept of followers.
We measure throughput but not write amplification. A single user write becomes: WAL write + memtable + SST flush + potential compaction. Real tuning targets WA, not raw throughput.
Our 4-byte LEN caps records at 4GB. RocksDB uses a variable-length integer (VarInt32/64) to save space on small records, which most WAL records are (<256 bytes).
Production WALs separate the flush/fsync into a dedicated sync thread with a bounded queue. This decouples append latency from fsync latency and enables better backpressure.
Build a WebSocket gateway from raw protocol upgrade to presence and backpressure to reconnect tokens with message replay — understanding why 10,000 connections need exactly two goroutines each.
Our hub is single-process. 10 gateway instances each have their own Hub. Broadcasting across instances requires Redis Pub/Sub or a message bus — every gateway subscribes to the room channel and fans out locally.
RFC 7692 allows compressing WebSocket payloads using deflate. For JSON messages, this achieves 60-80% compression. Implementation requires per-connection deflate context management and handshake extension negotiation.
A malicious client can flood the hub with messages at millions of frames/sec. Real gateways enforce a message rate limit per connection (e.g., 100 msg/sec) and disconnect violators.
Our gateway allows anyone to join any room. Production gateways validate a JWT on connection upgrade and check room membership in a separate auth service before allowing join.
Text JSON frames are easy to debug but 3-5x larger than equivalent binary frames. Real-time games use binary protocols (MessagePack, FlatBuffers) to hit sub-millisecond message delivery.
WebSocket connections are long-lived. An L7 load balancer must route all frames from a connection to the same backend (sticky sessions). Without this, frames from the same connection arrive at different backends.
