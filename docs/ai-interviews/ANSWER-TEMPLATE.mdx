## What they're really asking

{/* 40–90 words. The skill or signal underneath the wording: what a strong answer has to show,
    and where the round is decided (often the follow-ups). Don't restate the prompt; it is
    printed above the card. If you say what a company looks for, cite the report. */}

Can you keep an expensive, batch-friendly resource busy without letting any single caller wait too long, and
can you say what happens when it breaks? The one-GPU framing is a warm-up. The follow-ups (when to flush, how a
waiting caller gets its result, a GPU dying mid-batch, several GPUs) are where the round is decided.

## Clarify first

{/* 50–120 words. 3–6 questions you'd ask before designing, each with the assumption you'd
    write down if the interviewer doesn't answer. Mark assumed constants as assumptions. */}

- Is one input a fixed-cost forward pass, or a generation with variable output length?
- Does batch time grow with batch size? Ask for a rough cost model, or state one.
- What latency budget do callers have, and when do they give up?
- Arrival rate and burstiness, and whether a retry is safe.

Write each assumption down. The family walkthrough uses `T(b) = a + c × b` with `a` = 40 ms and `c` = 0.6 ms,
chosen so a full batch of 100 takes 100 ms. Those constants are assumptions, not measurements.

## Answer

{/* 150–400 words. The answer in the order you'd say it out loud: the design or the
    explanation, the one calculation that matters (<Formula> with vars and a worked example),
    and the failure case. ### sub-headings are fine for a multi-part answer. Point to the
    family walkthrough for depth instead of repeating it. */}

Put a bounded queue in front of the GPU. A batcher pulls up to 100 inputs whenever the GPU is free, so under
load the batch fills itself: requests that arrive during one batch become the next.

<Formula
  title="Self-clocking batch size"
  expr="b* = λ × a ÷ (1 − λ × c)     (stable while b* ≤ 100)"
  vars={[
    { sym: 'λ', meaning: 'arrival rate, requests per second' },
    { sym: 'a, c', meaning: 'fixed and per-input batch cost, in seconds' },
  ]}
  example="λ = 500/s: 500 × 0.04 ÷ (1 − 0.3) = 28.6 per batch, about 57 ms per batch"
/>

Each caller parks a future keyed by request id; the worker completes it when the batch returns. Deadlines travel
with the request, so the batcher drops work whose caller has already given up. Bound the queue by time: past
the point where a new request would miss its deadline, reject it at once. If a GPU dies mid-batch, requeue the
batch with a retry limit, and bisect a batch that keeps failing to find the poison input.

## Small-team version

{/* 60–150 words. You own AI at a 50–500 person company with a few engineers plus AI agents.
    What do you actually build, buy or skip for this problem, and what do you still own and
    verify yourself? Say what would make you revisit the decision (scale, cost, a compliance
    need). Keep vendor or product claims sourced (<Cite>), or phrase them as something to check. */}

At a 50–500 person company you rarely own this layer. If you call a hosted model API, the provider batches for
you. If you self-host, use a serving engine that batches internally and check its documentation for how. What
you still own: per-tenant admission control, request deadlines, timeouts on the client, and a dead-letter path
for inputs that keep failing. An agent can write the batcher; you write the test that kills a worker mid-batch.

## Pitfalls

{/* 3–5 bullets: a mistake candidates make here and, in a few words, what to do instead.
    <Pitfall> works too if one mistake needs a paragraph. */}

- Flushing only on a fixed timer, so the GPU idles while a half-full batch waits.
- An unbounded queue: latency grows without limit and every caller times out together.
- Retrying a poison input forever, taking the whole batch down each time.
