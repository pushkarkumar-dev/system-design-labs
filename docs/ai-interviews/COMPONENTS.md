# AI Interviews: components and rules

For agents writing guide pages (`src/content/interviews/guide/*.mdx`), family walkthroughs
(`src/content/interviews/walkthroughs/*.mdx`) and answer cards (`src/content/interviews/answers/*.mdx`).
Built by the foundation agent (A1), 2026-10-11; families, answer cards and question pages added by E0, 2026-10-12.

## Rules

1. **Don't import components in MDX.** Every component below comes from the shared map in
   `src/components/interviews/mdx.ts`, which the routes pass to `<Content components={…} />`. Using a
   component that isn't in the map fails the build. Need a new one? Ask the foundation owner.
2. **Ids must exist.** `Cite`, `Dated`, `LabRef`, `LabNumber`, `QuestionRow` and `CompanyCard` throw at build
   time if their id isn't in the data. That is deliberate: a broken reference never ships.
3. **Lab numbers only through `<LabNumber>`.** It labels every number "measured on …", "calculated" or
   "estimated" from the lab's frontmatter. A number counts as measured only if `measuredOn` contains a date
   (YYYY-MM-DD) and nothing says "estimated". Never type a lab benchmark into prose.
4. **Formulas over multipliers.** Use `<Formula>`; it requires `vars` and a worked `example`.
5. **Dollar signs are plain text.** Single-`$` math is off site-wide, so `$120K` is safe. There is no KaTeX
   in interview pages; don't use `$$…$$` either.
6. **Tables**: plain markdown tables are fine; they're wrapped automatically so they scroll sideways on
   phones.
7. **Inline JSX attributes**: strings in `"…"`; arrays/objects in `{…}`. Use `class`, not `className`.
8. **Headings**: guide pages use `##` for sections (they feed the sticky table of contents when a page
   has three or more) and `###` inside. Walkthrough H2s are fixed (see below).
9. **Links**: write internal links in MDX as full paths with the base and a trailing slash, e.g.
   `[question bank](/system-design-labs/interviews/questions/)`. Every question has its own page at
   `/system-design-labs/interviews/questions/<id>/` (its answer card lives there); the bank row is
   `/system-design-labs/interviews/questions/#q-<id>`. In `.astro` files use `url()` / `links.*` from
   `src/lib/interviews/url.ts` (`links.questionPage(id)`, `links.question(id)` for the bank row).
   `node tools/check-links.mjs` checks every one.

## Data and checks

- Data lives in `src/content/interviews/{sources,questions,companies}.yaml` (maps keyed by id; generated by
  `tools/interviews/staging.py merge`, so edit the staged files, not these).
- `src/lib/interviews/integrity.ts` runs on every interview page and fails the build with a list of
  problems: unknown source/lab/question/walkthrough ids, duplicate YAML ids, empty collections, confidence
  higher than its sources allow (snippet-only ⇒ low; only aggregator/secondary/news/snippet ⇒ at most
  medium), a walkthrough lab with role `proof` whose status isn't `proof`, unknown `gapLabs`, a lab named
  `interviews`, two walkthroughs with the same `family`, and for answer cards: a file name that isn't the
  question id, an unknown question, family or lab, a second card for the same question, a family whose
  `basedOn` doesn't list the card's question, a **published** card whose family walkthrough is a draft, and
  (for cards this build renders) a missing, extra or out-of-order H2.
- Warnings only (printed again at the end of `tools/interviews/locked-build.sh`): "N of 278 questions have
  no published answer", a question listed in more than one family walkthrough, a card or walkthrough outside
  its word range, a published walkthrough that still has `<MyTake pending />`, a `family` that differs from
  the file name, a legacy `walkthrough:` field on a question that names a deleted walkthrough, and a company
  whose `lastVerified` is older than 180 days.
- `src/lib/interviews/labStatus.ts`: `proof | partial | not-llm | needs-measurement` per lab, the caveat
  `LabRef` shows, and `PLANNED_LABS` (valid `gapLabs` keys). Labs not listed are `needs-measurement`.

## Family walkthroughs

Start from `docs/ai-interviews/WALKTHROUGH-TEMPLATE.mdx` (every frontmatter field, every component).
File name = id. `status: draft` pages are visible only in `npm run dev` or with `PUBLIC_SHOW_DRAFTS=true`.

A family walkthrough covers one underlying problem. Its `basedOn` lists every question in the family (give
each question one family), and each of those questions gets an answer card whose `family:` is this file name.
Frontmatter beyond the original fields:

- `family` (string, lowercase-kebab): the family id, **equal to the file name**. Setting it makes
  `## Small-team version` required. The 12 pre-family walkthroughs don't set it.
- `smallTeamFocus` (optional, ≤240 chars): one line on what a small team builds, buys or skips; shown in the
  header box.
- `format`: `design | coding | estimation | deep-dive | behavioral` (`narrative` parses but has no skeleton).

Required H2s, exact text and order, nothing extra (checked in `walkthroughs/[id].astro` against
`src/lib/interviews/skeletons.ts`). Small-team version is required when `family` is set, and always for
deep-dive and behavioral; a walkthrough without `family` may include it in the same place.

| Format | H2s in order |
|---|---|
| design | The prompt · What is being tested · Clarify and scope · Back-of-envelope · High-level design · Deep dives · Failure modes and overload · Evals and observability · Trade-offs · **Small-team version** · Senior vs Staff · Follow-ups · Common mistakes · Prove it with a lab · My take · Sources |
| coding | The prompt · What is being tested · Clarify and scope · Plan before code · Solution in stages · Verification · Complexity and performance · **Small-team version** · Senior vs Staff · Follow-ups · Common mistakes · Prove it with a lab · My take · Sources |
| estimation | The prompt · What is being tested · Clarify and scope · Constants (dated) · Derivations · Sanity checks · What changes the answer · **Small-team version** · Senior vs Staff · Follow-ups · Common mistakes · Prove it with a lab · My take · Sources |
| deep-dive | The prompt · What is being tested · Clarify and scope · Core concepts · Worked examples · Common follow-ups in depth · **Small-team version** · Senior vs Staff · Follow-ups · Common mistakes · Prove it with a lab · My take · Sources |
| behavioral | The prompt · What is being tested · What a strong story contains · Story structure · Example story outlines · **Small-team version** · Senior vs Staff · Follow-ups · Common mistakes · My take · Sources |

The body must also use `<AINative>`, `<LevelContrast>` and `<FollowUps>` with at least 5 `<FollowUp>`
items (all formats; mentions inside comments or code don't count). 2,500–5,500 words; outside that range is
a warning.

The page adds two things you don't write: a **Questions in this family** section (every `basedOn` question,
linked to its question page, with companies and whether its card is out) inserted right before
`## Sources` and in the TOC, and a header-box link to it.

`My take` is written by the site author only: use `<MyTake pending />`. A **published** walkthrough may keep
it: production builds render nothing for it and drop the "My take" heading and TOC entry; dev and
`PUBLIC_SHOW_DRAFTS=true` builds show the placeholder.

## Answer cards

Start from `docs/ai-interviews/ANSWER-TEMPLATE.mdx` (frontmatter, guidance per section, a worked example).
One card per question at `src/content/interviews/answers/<question id>.mdx`, rendered on the question's page
`/system-design-labs/interviews/questions/<id>/` below the question, its sources and confidence, and above a
Family box (family walkthrough + sibling questions) that the page adds.

```yaml
question: infra-001            # = the file name
family: llm-batcher-to-fleet   # family walkthrough file name; its basedOn must list infra-001
status: draft                  # draft | published (published needs the family published)
labs: [rate-limiter]           # optional lab slugs, shown under "Prepare with"
updatedAt: "2026-10-12"
```

Required H2s, exact text and order, nothing else at H2 (`###` inside is fine):
What they're really asking · Clarify first · Answer · Senior vs Staff · Small-team version · Pitfalls ·
Go deeper. 350–900 words (warning outside). Same component map and rules as walkthroughs;
`<LevelContrast>` under Senior vs Staff and `<LabRef inline>` under Go deeper are recommended, not enforced.
Draft cards show only in dev / `PUBLIC_SHOW_DRAFTS=true`; without a visible card the question page says
"Answer coming" and links the family walkthrough if one is visible. In the bank and in every `<QuestionRow>`,
"Answer →" appears when a visible card exists, and the walkthrough link goes to the card's family.

## Component reference

### Citations

**`<Cite id label? />`**: link to a source with its publisher, type and date.
- `id` (required): source id from `sources.yaml`. `label`: replaces the publisher as link text.
```mdx
Candidates report the values round as the hardest (<Cite id="s-42f1c7f6dd" />).
```

**`<Dated asOf src>claim</Dated>`**: a time-sensitive claim followed by "(as of Feb 2026 · Publisher)".
- `asOf` (required): `YYYY`, `YYYY-MM` or `YYYY-MM-DD`. `src` (required): a source id or an array of ids.
```mdx
<Dated asOf="2026-02" src="s-810bf5f1ff">Meta's AI-enabled round replaces one of its two coding rounds</Dated>.
<Dated asOf="2026-02" src={["s-810bf5f1ff", "s-c670decb7a"]}>…</Dated>
```

**`<SourceTag type? confidence? />`**: source-type pill and/or confidence pill.
- `type`: `official | first-hand | aggregator | secondary | news | snippet`. `confidence`: `high | medium | low`.
```mdx
<SourceTag type="first-hand" confidence="medium" />
```

### Numbers and labs

**`<Formula expr vars example title? note? />`**: monospace formula, variable legend, worked example.
- `expr` (required) string. `vars` (required, ≥1): `[{ sym, meaning }]`. `example` (required): string or
  array of strings. `title`, `note`: optional.
```mdx
<Formula
  title="KV cache per token"
  expr="bytes per token = 2 × layers × n_kv_heads × head_dim × bytes_per_value"
  vars={[{ sym: 'n_kv_heads', meaning: 'KV heads (fewer than query heads under GQA)' }, …]}
  example="Llama-3-70B in bf16: 2 × 80 × 8 × 128 × 2 = 327,680 B ≈ 320 KiB per token"
/>
```

**`<LabRef lab role? note? inline? />`**: links a lab and shows its status and caveat. Never shows numbers.
- `lab` (required; `slug` is an alias): lab slug. `role`: `proof | background | partial` (`proof` throws
  unless the lab's status is `proof`). `note`: one sentence on what the lab covers here. `inline`: a link with
  a status pill (caveat on hover) instead of a card.
```mdx
<LabRef lab="rag" role="proof" note="Dense, hybrid and reranked retrieval, built stage by stage." />
Read the <LabRef lab="llm-inference" inline /> lab first.
```

**`<LabNumber lab metric showMetric? />`**: quotes one benchmark row with its provenance label.
- `lab` (required): slug. `metric` (required): the row's `metric` text, exact or a unique case-insensitive
  substring (the error lists the available metrics). `showMetric`: print the metric name too.
```mdx
Per-group INT4 error is <LabNumber lab="model-quantizer" metric="INT4 weight error, one scale per 32 weights" />.
```

### Questions and companies

**`<QuestionList track? theme? featured? limit? group? level? idPrefix? />`**: server-rendered rows grouped by
theme in rank order.
- `track`: `ai-engineer | ai-infra | both` (a track also includes `both` questions). `theme`: a theme id.
  `featured`: only featured rows. `limit`: max rows. `group` (default true): theme headings. `level`
  (default 3): heading level. `idPrefix`: keeps heading ids unique if a page has several lists. (`bank` is
  for the questions page only.)
```mdx
<QuestionList track="ai-infra" featured />
<QuestionList theme="rag" limit={5} idPrefix="rag-top" />
```

**`<QuestionRow id />`**: one question (anchor in the bank is `#q-<id>`).
```mdx
<QuestionRow id="infra-001" />
```

**`<CompanyCard id open? />`**: a company's loop, AI policy, notes, sources and last-verified date in a
`<details id="c-<id>">`. **`<PolicyMap kind? detail? />`**: the AI-tool policy table (`detail={false}` drops
the long column; `kind="frontier-lab"` filters).
```mdx
<CompanyCard id="anthropic" open />
<PolicyMap detail={false} />
```

### Walkthrough blocks

**`<LevelContrast title? senior? staff?>`**: Senior vs Staff columns (stack on phones). Pass string arrays,
or markdown through named slots. Both sides are required.
```mdx
<LevelContrast title="Batching" senior={["Sizes the batch from the latency budget."]} staff={["Asks who owns the budget."]} />

<LevelContrast title="Batching">
  <Fragment slot="senior">Sizes the batch from the **latency budget**.</Fragment>
  <Fragment slot="staff">Asks who owns the budget and what breaks first.</Fragment>
</LevelContrast>
```

**`<FollowUps title?>` + `<FollowUp q open?>answer</FollowUp>`**: each follow-up is a `<details>`.
```mdx
<FollowUps>
  <FollowUp q="One GPU in the pool dies mid-batch. What happens to those requests?">
    Markdown answer.
  </FollowUp>
</FollowUps>
```

**`<AINative title?>…</AINative>`**: the agent-era angle (required once per walkthrough).
**`<Pitfall title?>…</Pitfall>`**: a common mistake.
```mdx
<AINative title="Who verifies the batcher?">How directing agents changes this, and what you still check.</AINative>
<Pitfall title="Unbounded queues">What goes wrong and what to do instead.</Pitfall>
```

**`<MyTake pending? />`**: `pending` renders the "Author's take — to be written" placeholder (dev and
`PUBLIC_SHOW_DRAFTS` builds only; production renders nothing); otherwise the slot is the author's text.
```mdx
<MyTake pending />
```

**`<Figure caption wide?>svg</Figure>`**: wrapper for a hand-drawn inline SVG. Draw with `currentColor` and
`var(--fig-ink | --fig-muted | --fig-line | --fig-accent | --fig-bg | --fig-warn)`; never hex colours, so it
works in both themes. Give the `<svg>` a `viewBox`, `role="img"` and an `aria-label`.
```mdx
<Figure caption="Requests queue in front of a batcher.">
  <svg viewBox="0 0 400 80" role="img" aria-label="Queue feeding a batcher">
    <rect x="10" y="20" width="100" height="40" rx="6" fill="none" stroke="currentColor" />
    <text x="60" y="45" text-anchor="middle">queue</text>
  </svg>
</Figure>
```

## Page-level pieces (not in the MDX map)

- `InterviewLayout` (`title`, `description`, `researchedAt?`, `updatedAt?`, `eyebrow?`, `wide?`, `toc?`,
  `docTitle?` (shorter browser-tab title), `compactTitle?` (smaller H1 for long titles), slots `meta` and
  `aside`): shell for every interview page; runs the integrity check; shows "Researched <date>"
  (frontmatter date, or the latest date in the data).
- `src/pages/interviews/questions/[id].astro`: one page per question (question, sources, answer card,
  Family box). `FamilyQuestions` (`w`, `exclude?`, `bare?`): a family's question list, used there and on
  walkthrough pages. `WalkthroughH2`: the `h2` override the walkthrough page passes to its MDX (inserts
  "Questions in this family" before Sources, hides a pending My take in production).
- `src/lib/interviews/data.ts`: `visibleAnswer(d, id)`, `hasPublishedAnswer(d, id)`, `familyOf(d, id)` (the
  visible card's family, else a visible walkthrough listing the question, else the legacy `walkthrough:`
  field), `companyNames(q)`.
- `InterviewSubNav`: the tab strip. `WalkthroughCard` (`w`): index card. `TableScroll`: the `table` override.
- `src/components/ui/ChipGroup.astro` (`name`, `label`, `options: {value,label,count?}[]`, `allLabel?`,
  `multi?`) + `src/scripts/chip-filter.ts`: chip and search filtering for any server-rendered list.
  Contract: a root `<div data-chip-filter="#list" data-count-noun="question|questions" hidden>` holding
  ChipGroups, an `<input data-filter-search="q">` and `[data-filter-clear]`; items carry `data-filter-item`,
  `data-<name>="space separated tokens"` and `data-search`; optional `[data-filter-section]` (hidden when
  empty, `[data-section-count]` updated), `[data-filter-count]`, `[data-filter-empty]`. State lives in the URL
  (`?track=…&round=a,b&q=…`); chip clicks push history so back/forward work; the root stays hidden without JS.

## Commands

Several agents share this working tree, so build only through the lock:

```bash
tools/interviews/locked-build.sh                          # production build + link check
PUBLIC_SHOW_DRAFTS=true tools/interviews/locked-build.sh  # include draft walkthroughs and cards
tools/interviews/locked-build.sh --force                  # bypass the content cache (after YAML edits)
```

It prints the tail of the build (or the whole error when it fails), then every `[interviews]` warning once,
then runs `node tools/check-links.mjs` (internal links + #anchors in dist/).
