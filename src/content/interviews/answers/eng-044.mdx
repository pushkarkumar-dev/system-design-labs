## What they're really asking

> **If you only remember one thing, say this in the first minute:**
> "I'd start from the chatbot's job and its real failures, not from a list of metric names. I read 50 to 100
> real conversations and write down how it fails. If it answers from documents, I measure the search step
> and the writing step separately. I grade with code checks first, then with an AI grader that I've checked
> against people, then with people on a sample. I compare versions on the same test cases, several runs
> each, with an error bar. And in production I watch whether users' problems actually got solved."
>
> The rest of this page explains each part of that answer.

This is an open question. It tests whether you start from the chatbot's job and its failures, or from a list
of metric names. A strong answer is short and structured: what good means, how you grade it, how you compare
versions, and how you watch it in production.

### What makes this different from evaluating normal software

For normal software you write tests that assert an exact output. A chatbot built on a large language model
(**LLM**) breaks that:

1. **There's rarely one right answer.** Many replies are correct, so string matching can't grade them.
2. **The same input can give a different reply each time.** One run of a test proves little.
3. **A wrong answer can have several causes.** The bot may have found the wrong document, or found the right
   one and misread it. These need different fixes, so you need to tell them apart.

The report is low confidence: a candidate account of OpenAI interviews on Exponent's Medium, seen only
second-hand (<Cite id="s-9ffe6685c2" />).

### Words you need first

- **RAG** (retrieval-augmented generation): the bot first searches a set of documents (**retrieval**), then
  the model writes an answer from what it found (**generation**).
- **Failure mode**: a named, recurring kind of failure that you can count, such as "ignored an earlier turn".
- **LLM judge**: a second model call that grades a reply against one written rule and returns pass or fail.
- **Trial**: one run of one test case. Because replies vary, each test case gets several trials.

## Clarify first

- **What does the chatbot do?** Answering from documents, taking actions, or open conversation each need
  different checks.
- **Who uses it, and what does a bad answer cost?**
- **Single-turn or multi-turn?** Multi-turn needs checks on the whole conversation, not only the last reply.
- **Is there labelled data, or a domain expert who can label?**

## Answer

### Five steps, in order

**1. Define good from real conversations.** Read 50–100 transcripts. Write down the failure modes: wrong
facts, answers not supported by the sources, ignoring earlier turns, failing to hand off to a person, unsafe
content. Decide which are must-not-happen: one failure blocks a release.

**2. Separate retrieval from generation** if it is a RAG bot.

```
User question
   │
   ▼
Retrieval ── search the documents      → measure: was the right document found?
   │                                     (recall@k or hit rate on labelled questions)
   ▼
Generation ── model writes the answer  → measure: does the answer stick to what was found
   │                                     (faithfulness), and does it answer the question?
   ▼
Reply
```

**Recall@k** is the share of the relevant documents that appear in the top k search results. **Hit rate**
is the share of questions where at least one correct document appears in the top k. **Faithfulness** means
the answer says only what the retrieved passages support. A wrong answer with the right document retrieved is
a different bug from a missing document.

**3. Grade cheaply first.** Code checks for format, citations and policy limits. Then one pass/fail judge per
open-ended failure mode, checked against human labels before you trust it. A human sample for the rest.

**4. Compare versions properly.** Run both versions on the same items, several trials each, and compute the
difference with an error bar. For a customer-facing bot, also care about consistency (next section).

**5. Watch production.** Task success or resolution, escalation and recontact rates (customers coming back
about the same issue), thumbs and complaints, latency and cost, plus a weekly read of sampled transcripts.
Feed every failure back into the test set.

Say: "I start from how it fails, and I keep the search step and the writing step separate, because they
break differently."

### Follow one chatbot: why consistency matters

Say your support bot succeeds on a task 75% of the time per trial. Two ways to score three trials give very
different pictures:

| Score | What it means | Result at 75% per trial | When to use it |
|---|---|---|---|
| **pass@3** | At least one of three trials succeeds | **about 98%** | A user can retry and pick the best answer |
| **pass^3** | All three trials succeed | **about 42%** | A customer gets one try, so the bot must be consistent |

The 42% is Anthropic's worked example; the 98% is derived from the same numbers. The same bot looks excellent
by one score and unreliable by the other.

Say: "A customer gets one try. For a customer-facing bot I measure whether it succeeds every time, not
whether it succeeds once in three."

In the Senior column, "calibrated" means checked against human labels, and "paired intervals" means
comparing both versions on the same items with an error bar on the difference.

## Small-team version

- **Week 1:** 50 items from real failures, with code checks running in CI.
- **Then:** grow to a few hundred items, with one judge per failure mode.
- **Use** the tracing you already have. **Build** the test set yourself.

The cost is the domain expert's labelling, not tooling. Reading 100 transcripts at an assumed 2 minutes each
is **about 3.3 hours** (200 minutes). A 200-item, 3-trial judged suite on a single-call bot is **about $13 per run** at list
prices fetched 2026-10-11 (family walkthrough).

## Pitfalls

- **Answering with BLEU, ROUGE or a generic "helpfulness" score.** These measure word overlap or a vague
  quality, not whether the user's problem was solved.
- **One end-to-end score.** It hides whether retrieval or generation failed, so you don't know what to fix.
- **Single-trial evaluation of a bot whose replies vary.** One lucky run looks like success.
