## What they're really asking

> **If you only remember one thing, say this in the first minute:**
> "I use AI every day, and I treat what it produces as a draft that I check. For bug fixes I hand a coding agent
> the failing test and approve its plan before it writes code, then I read the whole diff. Once it wrote a
> database migration that passed every test but would have locked our largest table; a staging run caught it,
> and I added a check to CI so it can't happen again. I don't use it with customer data or for schema
> migrations."
>
> The rest of this page explains each part of that answer, so you can say it with your own examples.

The interviewer wants to know one thing: do you use AI as a **draft you check**, or as an **answer you trust**?

This is not like an ordinary behavioral question about a conflict or a deadline. Almost every engineer now
says they use AI, so "I use it a lot" tells the interviewer nothing. And AI tools are wrong in a convincing way:
they write wrong code with the same confidence as right code. So the question is really about your checking
habits, and the second half of the question (the bad output) is where the answer is decided.

The title is a PracHub listing tagged Amazon, posted 2026-10-02; only the title is candidate-reported, and the
body is PracHub's own write-up (<Cite id="s-56187f9727" />). That write-up says strong answers give "Concrete,
first-person examples rather than general opinions about AI" and "A consistent verification habit, with AI
output treated as a draft to be checked." Its hint for the bad-output part is "Name what caught it."

### Words you need first

- A **large language model (LLM)** is a program trained on a huge amount of text and code that predicts what
  text should come next. Coding tools are built on one.
- A **coding agent** is an AI tool that does more than suggest code. It reads files, edits several of them, runs
  commands and tests, and keeps going until it thinks the task is done.
- A **hallucination** is a confident answer that is false. In code, the usual case is an **invented API**: a
  function or option that looks real and doesn't exist in your library version.
- A **rule file** is a plain text file in the repository (often `AGENTS.md`) that the agent reads at the start of
  every task: conventions, commands, and "never do X" lines.

## Clarify first

PracHub's write-up suggests some clarifying questions. They are sensible ones to ask:

- **Data rules.** "Should I describe how my employer's rules on which tools may see code or data shaped my use?"
  Yes, briefly. It shows judgment.
- **Scope.** "Can I include non-coding work, such as design docs, debugging or learning a codebase?"
- **Kind of harm.** "By wrong or harmful, do you mean a correctness bug, or something that harmed users?" Have one
  of each if you can.

## Answer

### The example we will follow

This page follows one illustrative engineer, Sam, a backend engineer on an orders service written in Go. Sam
has used one coding agent daily for about six months. Use the shape, with your own facts.

### Part 1: daily use, about two minutes

Give a four-beat answer: **workflow, check, failure, limit**. Here is Sam's, with a rough clock:

| Clock | Beat | What Sam says (illustrative) | Why it works |
|---|---|---|---|
| 0:00 | **Workflow** | "For bug fixes I give the agent the failing test and the package, ask for a plan, approve it, then let it write the change. I also use it to explain code I haven't seen before." | Names the input, the action and the output. |
| 0:40 | **Check** | "I read the full diff and run the race detector. For explanations, I check two of its claims against the code before I trust the rest." | Every workflow has its own check. |
| 1:10 | **Failure** | "Once it wrote a migration that passed every test but would have locked our biggest table. Staging caught it." | One sentence. It is the hook for Part 2. |
| 1:30 | **Limit** | "Since then I write migrations myself, and I never put customer data in external tools, which is our policy." | Ends on judgment. |

"I use it for everything" is not a workflow. A workflow says what goes in, what the tool does and how you check
what comes out.

The loop behind that answer is a small system, and picturing it keeps you in order:

```
Task (failing test + package)
   │  1. hand over something checkable
   ▼
Agent proposes a plan ── you approve or correct it
   │  2.
   ▼
Agent edits code and runs the tests
   │  3.
   ▼
Your review ── full diff, race detector, staging for risky changes
   │  4.
   ▼
Merge
   │  5. a mistake got through, or nearly did?
   ▼
Rule file + new CI check ── so the same mistake is caught next time
```

**The task.** Start from something the agent can be checked against, like a failing test. **The plan.** Reading
a short plan before any code exists is the cheapest place to catch a wrong direction. **The test run.** Passing
tests are necessary, not enough: the agent wrote code to pass *those* tests. **Your review.** This is the step the
interviewer listens for. **The rule file.** Each mistake becomes a rule or a check, so the system gets better.
Mitchell Hashimoto describes turning each agent mistake into an AGENTS.md rule or a tool
([mitchellh.com, 2026-02-05](https://mitchellh.com/writing/my-ai-adoption-journey)).

### Don't quote a speed-up you haven't measured

Feeling faster and being faster are different. In a 2025 study by the research group METR, experienced
developers believed they were about 20% faster with AI tools while measuring 19% slower
([METR, 2025-07-10](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)). Say it like this:
"I haven't measured my speed-up properly, so I won't give you a percentage. I can tell you what shipped and how
I checked it."

### Part 2: wrong or harmful output

This is the story the interviewer remembers. It has four parts:

1. **The output, and why it looked right.** A migration, an invented API, a security hole, a confident wrong
   summary. Explain why a reasonable engineer could have missed it.
2. **What caught it.** A test, a reviewer, staging, a production metric, a customer. If it reached production,
   say so.
3. **The cost.** Time lost, a near miss, or a real incident.
4. **What you changed** so that kind of error is caught earlier: a line in the rule file, a new kind of test, a
   review step.

Sam's story, step by step (illustrative):

| Step | What happened | What to say in the interview |
|---|---|---|
| **Plausible error** | The agent wrote a migration. It passed every test, because the test database was tiny. | "It looked right, and the tests agreed." |
| **What caught it** | A staging run on a copy of production data showed it locked the large orders table. | "Staging with real data volumes caught what unit tests couldn't." |
| **Cost** | Half a day; nothing reached production. | "A near miss, not an incident." |
| **Change** | A rule in the agent's instructions, a lock-duration check in CI for every migration, and migrations written by hand. | "The gap was in my checks, so I closed it for everyone." |

Notice what the story is about. It is not "the AI was bad". It is "my checks had a gap, here is what caught it,
and here is the check I added". A story where the tool is the villain hides the lesson.

If you need a second story, security is a good place to look. Veracode's 2025 test of 100+ models on 80 tasks
found a vulnerability in 45% of generated code ([Veracode, 2025-07-30](https://www.veracode.com/press-release/ai-generated-code-poses-major-security-risks-in-nearly-half-of-all-development-tasks-veracode-research-reveals/)).

### Part 3, if asked: a RAG project

**RAG** (retrieval-augmented generation) means looking up relevant documents in a search index and pasting them
into the model's input, so it answers from those documents rather than from memory. The PracHub page also lists
a RAG walkthrough, with follow-ups about detecting answers from outdated documents and handling questions the
documents don't cover. Be ready to say whether a bad answer came from **retrieval** (the search found the wrong
or stale document) or from **generation** (the model had the right document and still answered wrongly). Say
it like this: "First I check what the search returned. If the right document was there, it's a generation
problem; if not, it's a search problem, and the fixes are different."

In plain words: the Senior answer is about your own habits. The Staff answer is about what you changed for
everyone. Sam's CI lock check is the start of a Staff answer, because it protects every migration, not only
Sam's.

## Small-team version

At a company hiring its first AI engineer, this answer is evidence of whether you will make the team's AI use
safer or riskier. Nobody else will catch your agent's mistakes, so the failure story matters even more. Add
what you would set up for others:

- **Which tools may see which data**, written down in one page.
- **A review rule** for agent-written changes, and plan approval before the agent writes code.
- **A shared rule file** that grows with each agent mistake.
- **A spend cap.** Coding agents on a provider's API are billed per **token** (a chunk of text of roughly ¾ of a
  word). On the family walkthrough's assumed usage, one engineer's agent costs about **$69 a month**, so ten
  engineers is about $690.

<details>
<summary>The arithmetic behind the numbers (for a Staff-level follow-up)</summary>

- **Assumed use per engineer per day:** 2M input tokens, of which 1.6M are **cache reads** (repeated text the
  provider charges less for), and 0.2M output tokens.
- **Claude Sonnet 5 list prices, fetched 2026-10-11:** $2 per million input, $0.20 per million cached input, $10
  per million output.
- **Per day:** 0.4M × $2 + 1.6M × $0.20 + 0.2M × $10 = $0.80 + $0.32 + $2.00 = $3.12.
- **Per month:** $3.12 × 22 working days ≈ $69; ten engineers ≈ $690.

</details>

Say it like this: "I'd buy one approved assistant with a spend cap, write the data rules down, and add a CI check
every time an agent mistake gets close to production."

## Pitfalls

- **Enthusiasm with no workflow.** It tells the interviewer you use AI, not that you use it well.
- **A failure story that blames the tool.** It hides the gap in your own checks, which is the lesson they want.
- **An unmeasured productivity percentage.** Studies show people's sense of their own speed-up is unreliable, so
  a made-up number costs credibility.
- **Ignoring data-handling rules.** Rules on which tools may see code and data are a real constraint at most
  employers, and skipping them suggests you haven't thought about it.
