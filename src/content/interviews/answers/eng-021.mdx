## What they're really asking

> **If you only remember one thing, say this in the first minute:**
> "Before drawing anything I'd ask what the agent is for and what it may do: which customer requests carry the
> volume, which actions it can take alone, and which metric decides. Then the design is a support agent whose model
> only proposes the next step, answer, call a tool, or hand off, while code checks every step, caps anything that
> moves money, and stops the loop. The streaming-specific part is a playback-diagnosis tool, and the sensitive part
> is cancellation. Load is tiny; cost and correctness are the constraints."
>
> The rest of this page explains each part of that answer.

"Design an AI agent for a streaming service" is a vague prompt on purpose. The interviewer wants to see you turn it
into something buildable: who uses it, what they ask, what the agent may do, and how you'll know it works. Only then
do you draw boxes.

Why does an AI agent need different scoping from a normal support tool? In a normal tool, your code decides every
path. In an agent, a **large language model (LLM)**, a program that reads text and writes text, decides the next
step. It can misread a request, invent a policy, or be talked into a refund. So the first questions are about
**what the agent is allowed to do**, because the permissions and caps you set in code are what keep a wrong model
decision harmless.

<Cite id="s-5f98d711e8" />. With no detail, expect the interviewer to fill in gaps only when you ask.

## Clarify first

Ask, then state an assumption for each:

- **Who is the user?** Subscribers asking for help, or viewers asking for recommendations? "I'll assume support."
- **Which requests carry the volume?** "I'll assume billing questions, playback trouble, plan changes, credits,
  cancellation and account access." These kinds of request are called **intents**.
- **What can the agent do without a person?** "Reads, plan changes at the next renewal, and credits up to one
  month's fee."
- **Channels?** "Chat in the app first; voice later."
- **Volume?** "About 2,000 conversations a day for a mid-size service."
- **Which metric decides?** Containment, CSAT or cost per resolution? (Defined below.)

Say: "The policies decide the architecture, so I want them before I draw."

## Answer

### Words you need first

- **Token**: the unit a model reads and writes, roughly ¾ of a word. Providers charge per million tokens.
- **Tool call**: the model writes a structured request ("look up this invoice"); your code runs it and feeds the
  result back. The model never touches billing directly.
- **Hand-off**: moving the conversation to a human support agent.
- **Containment**: the share of conversations the bot resolves without a person. **CSAT** is the customer
  satisfaction score from the survey after a chat.

### Sort the intents by risk

| Group | Examples | What the agent may do |
|---|---|---|
| Answers | playback tips, devices, pricing | answer from the help center |
| Lookups | invoices, current plan, recent charges | read freely, for this customer only |
| Reversible actions | pause, switch plan at renewal, resend receipt | act after identity is verified |
| Money and irreversible | credits, refunds, immediate cancellation | act inside a cap, after the customer confirms; a person above the cap |

Cancellation is the sensitive one. It also triggers a retention-offer policy. A bot that makes cancelling hard
damages trust and may raise consumer-law questions to check with legal. Say: "The agent offers retention once, and
then it cancels."

### The design

```
Customer (app chat)
   │
   ▼
Conversation service ── login session, identity, owner flag (bot or human)
   │
   ▼
Orchestrator ── runs the loop with budgets; LLM proposes answer / tool / hand-off
   │
   ├──► Tool gateway ── tiers (read, reversible, money), caps in code ──► billing, accounts,
   │                                                                     playback logs, help center
   ├──► Human queue ── gets a summary plus a structured state object
   └──► Traces ── one per conversation
```

**Conversation service.** Holds the login session and the customer's identity. It also holds an **owner flag**,
bot or human, so the two never reply at once.

**Orchestrator.** Plain code that runs the loop. Each step it asks the model for one proposal: answer, call a tool,
or hand off. It checks the proposal, runs it, and stops the loop when a limit is hit (too many steps, the same call
repeated, no progress), handing off with the reason.

**Tool gateway.** The only path to backends. It applies the tiers in the table above. Caps such as "credits up to
one month's fee" live here, in code, so no prompt can change them. The customer id comes from the session, not
from the model.

**Help-center search.** One read-only tool that finds relevant articles.

**Human queue.** Receives a summary plus a **state object**: a small structured record of verified identity, ids in
play, actions taken and promises made. The person never re-asks.

**Traces.** One per conversation, with every model call and tool call recorded.

### Follow one conversation through it

Maya, on an assumed $15-a-month plan, writes: *"My TV app has crashed every night this week. I want this month
refunded."*

| Step | What happens | What to say in the interview |
|---|---|---|
| 1 | The model calls the playback tool. It returns her recent errors and device list: the TV app is two versions behind (illustrative). | "This tool turns a generic FAQ into a diagnosis. It is read-only, so the agent can use it freely." |
| 2 | The model answers with update steps and offers a $15 credit. | "The fix comes from data, not a guess." |
| 3 | Maya confirms. The gateway checks: $15 is within the one-month cap; it issues the credit with an idempotency key. | "Money moves only inside a cap in code, after a confirmation the model can't fake." |
| 4 | She asks for three months back. $45 is over the cap, so the gateway says "person". | "Policy says hand off, so the code hands off, whatever the model wanted." |
| 5 | A human agent gets the summary and state object, and takes ownership. | "The person starts where the bot stopped." |

### The numbers

Load is about **0.37 model calls a second**, which is trivial. Cost is the constraint. Every model call re-sends the
whole conversation so far, because the model keeps no memory between calls, so input grows quickly with
conversation length. A typical conversation is about **76,000 input tokens**, roughly **$0.09** on Claude Sonnet 5
at list prices with the fixed part of the prompt cached (**prompt caching** bills a repeated prompt start at a much
lower rate).

<details>
<summary>The arithmetic behind the numbers (for a Staff-level follow-up)</summary>

- **Load:** 2,000 conversations × 8 turns × 2 model calls ÷ 86,400 s ≈ **0.37 calls per second**.
- **Tokens:** the family walkthrough's formula with assumed inputs (8 turns, 2 calls per turn, a 3,000-token fixed
  prefix, 500 tokens of history added per turn) gives about **76,000 input tokens** per conversation without
  compaction.
- **Price:** roughly **$0.09 per conversation** on Claude Sonnet 5 at list prices fetched 2026-10-11 ($2 input,
  $0.20 cached input, $10 output per million tokens), with the fixed prefix cached.

</details>

### Metrics, in pairs

Each metric is paired with one that catches gaming it:

- containment, with repeat contact (did she come back about the same issue?);
- escalation rate, with how often the person resolves the hand-off without re-asking;
- CSAT on both paths, bot-only and handed-off;
- policy violations, such as a credit over the cap, held at zero.

Say: "Containment alone rewards a bot that refuses to hand off, so I always report it next to repeat contact."

## Small-team version

A streaming company of 50–500 people most likely already runs a helpdesk with an AI add-on. Start there for
help-center answers: Intercom listed Fin at $0.99 per outcome on 2026-10-12. Build only the action tools the vendor
can't call, or build the whole loop once volume passes the walkthrough's break-even.

At 2,000 conversations a day, Fin would bill about **$29,700 a month**, against about **$10,700** to own the loop.
Either way, own the test set (30–50 real conversations per intent), the caps on credits, and a dashboard of why
conversations stopped.

<details>
<summary>The arithmetic behind the numbers (for a Staff-level follow-up)</summary>

Assumed 50% containment: 60,000 conversations a month × 0.5 × $0.99 ≈ **$29,700** for Fin. Owning: about $5,400 of
tokens (60,000 × $0.09) plus about $5,300 a month for 20% of a loaded engineer and the amortized build, per the
walkthrough ≈ **$10,700**.

</details>

## Pitfalls

- **Designing before asking what the agent may do.** The policies decide the architecture.
- **Treating cancellation like any other write.** It carries retention policy, trust and possibly legal rules.
- **One accuracy number instead of paired metrics.** A single number can be gamed; pairs keep each other honest.
- **Forgetting that "title only" means scoping out loud.** The interviewer is waiting for your questions.
