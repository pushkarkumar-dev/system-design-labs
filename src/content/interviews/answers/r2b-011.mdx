## What they're really asking

> **If you only remember one thing, say this in the first minute:**
> "I'll use the assistant for narrow questions I can check quickly, not 'find the bugs'. Nothing it tells me counts
> until something runs: a test, a log line, a trace. I'll say out loud when I reject a suggestion and why. The
> debugging itself is the usual method: run, map, rank suspicions, failing test, smallest fix, explain. And I'll
> only optimize once the bugs are fixed, with before-and-after timings."
>
> The rest of this page explains each part of that answer.

The round is reported to grade three skills: "AI fluency, including prompt engineering, output validation, and
debugging skills" (<Cite id="s-b88d89c103" />). In plain words, **prompt engineering** means how well you word
your requests to the AI assistant, and **output validation** means checking what it tells you before you rely on
it. Here the assistant is **Gemini**, Google's large language model (LLM), which can read code and answer questions
about it.

What makes this different from a normal debugging round is that you have a second voice in the room, and it is
often wrong in a convincing way. A colleague who is unsure usually sounds unsure. An LLM sounds equally confident
when it is right and when it is wrong. So the interviewer is not only watching whether you find the bug. They are
watching whether you can tell the assistant's good answers from its bad ones, and whether you can show how you
told.

## Clarify first

Ask, and state an assumption for each:

- **Which language, and how large is the codebase?** "I'll assume one service, a few files."
- **Is the assistant chat-only, or can it edit files?** Ask at the start; it changes how you use it.
- **Is 'optimize' about speed, memory or readability?** "I'll assume speed, and I'll measure it."
- **What does 'done' look like:** a fix, a written explanation, or both?

## Answer

Treat the three graded skills as three habits you show on purpose. This page uses one example throughout: the
family's practice **URL shortener**, which turns a long link into a short code and redirects visitors back. Its
links can expire after a **TTL** (time to live) that the caller gives in milliseconds, while its clock counts
seconds.

### Habit 1, prompting: ask narrow, checkable questions

"Where is this value cached, and is it ever invalidated?" beats "find the bugs". Give the assistant the file and
the symptom, and ask for a hypothesis plus a test that would confirm it. A narrow question gets an answer you can
check in seconds. A broad one gets a long list that mixes real bugs with invented ones and misses the silent ones.

Good questions for the shortener:

- "List every place `resolve`'s result is cached."
- "Which callers pass seconds and which pass milliseconds?"
- "Write a test that resolves a deleted link."

### Habit 2, output validation: nothing counts until something runs

Here is the pattern on one exchange with the assistant:

| Step | What happens | What to say in the interview |
|---|---|---|
| 1. Ask | "When does a link with `ttl_ms=5_000` expire?" | "I'll ask, then check." |
| 2. The assistant answers | "TTL is in seconds, so this link expires after 5 s." | "That's a claim. Let me test it." |
| 3. Test the claim | Run the test below with a fake clock. | "The test sets the clock by hand, so nothing sleeps." |
| 4. Result | It fails on the original code. | "The claim was wrong: the link outlives 5 seconds, because milliseconds are added to seconds." |
| 5. Record it | Note the rejected claim. | "I'm rejecting the assistant's explanation; the units disagree." |

The test, using a fake `Clock` whose time the test sets directly:

```python
# The assistant claims: "TTL is in seconds, so this link expires after 5 s."
def test_claim_ttl_units():
    clk = Clock()
    s = Shortener(clock=clk)
    code = s.shorten("https://t.example", ttl_ms=5_000)
    clk.t += 6
    assert s.resolve(code) is None        # fails on the original: the claim was wrong
```

Saying out loud when you reject a suggestion, and why, is the visible evidence of output validation. Without the
narration, the interviewer only sees you typing.

<details>
<summary>The arithmetic behind the numbers (for a Staff-level follow-up)</summary>

- **TTL bug:** `ttl_ms=5_000` added straight to a clock in seconds makes the link live 5,000 seconds, about 83
  minutes, instead of 5 seconds. That is 1,000× too long, so a check 6 seconds later still finds it alive.

</details>

### Habit 3, debugging: the same method as any read-and-fix round

Run it. Map the entry points and the state. Rank your suspicions. Write the failing test. Fix. Explain.

One worked example from this guide's labs: the cdn-edge lab is a small cache that sits in front of an **origin**
server. It has a **stale-if-error** feature: when the origin fails, it should serve the older cached copy instead
of an error. Its stale-if-error test fails because a 5xx from the origin is returned as a successful fetch, so the
fallback never runs. A one-line change (treat a 5xx as an error) made it pass in a scratch copy (Go 1.26.9,
2026-10-12).

Say it like this: "The fallback only runs on an error. A 500 response isn't an error to this code, so I'll check
where the response status is turned into success or failure."

### Last, optimize, and measure

Profile or time the slow path first. Fix the accidental O(n²), or the work done on every request that could be done
once. Show the before and after numbers from your own run. Optimizing before the bugs are fixed gives you a faster
wrong answer.

## Small-team version

The plan's three skills describe a small team's daily work with coding agents. An agent proposes, you check its
claim against something that runs, and you fix with a test.

The rule to adopt: **an agent's diagnosis without a reproducing test is a guess, however fluent it sounds.** Buy
the assistant; the habit is the part you build.

At list prices, an agent session that reproduces and fixes one bug costs a few dollars. The
[drive-an-agent walkthrough](/system-design-labs/interviews/walkthroughs/ai-coding-drive-agent/#small-team-version)'s
assumed 40-step session is $6.84 uncached and $1.22 with **prompt caching** (a discount when the start of a prompt
repeats a recent one). That is far less than the review time the fix consumes, which is why the reproducing test,
not the explanation, is what you ask for first.

## Pitfalls

- **Pasting the whole codebase and asking "what's wrong?"** You get a long, unverifiable list.
- **Accepting a confident explanation without running anything.** Confidence is not evidence with an LLM.
- **Optimizing before the bugs are fixed.** A faster wrong answer is still wrong.
- **Drilling this format for a Senior or Staff loop where it isn't reported.** The plan names junior and mid-level
  roles only.
