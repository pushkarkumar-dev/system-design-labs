## What they're really asking

> **If you only remember one thing, say this in the first minute:**
> "I'd start from the docs as they stand today, because they changed in 2026: OpenAI is winding down its
> fine-tuning platform. So the strategy is: measure first and improve the prompt, because most teams never need
> to fine-tune. For each method, say what data it needs. And for anyone who already has fine-tuned models, list
> them, note when each base model shuts down, and move them before that date, either to a newer model with a
> better prompt or to an open model they can host."
>
> The rest of this page explains each part of that answer, so you can say it with understanding.

This is a take-home: read OpenAI's public docs and develop a strategy for its fine-tuning capabilities. It tests
three things. Can you read primary sources carefully? Can you turn them into a decision framework? And do you
notice what has changed? On this topic, a lot has.

First, the idea. A large language model (**LLM**) reads and writes text. **Fine-tuning** means training a model
further on your own examples so that its internal numbers (its **weights**) change. When you fine-tune on a
provider's platform, the result is a private copy of one of their models, called the **base model**, with your
changes on top.

For a backend engineer, the closest picture is a **fork of a hosted dependency that only the vendor can run**.
You don't hold the code. You can't move it elsewhere. And when the vendor retires the base model, your fork stops
working. That makes a fine-tuning strategy partly a technical question (when is it worth it?) and partly an
operations question (what happens to the forks you already have?).

The task is on a question list with no date, so treat its wording as approximate <Cite id="s-d7a8e88bf0" />.
"Strategy" could mean guidance for customers or product strategy for OpenAI; ask which.

## Clarify first

- **"Who is the audience?"** Customers deciding whether to fine-tune, or OpenAI deciding what to do with the
  product?
- **"Which docs are in scope?"** The optimization guide, the method guides, pricing and deprecations.
- **"What should I hand in?"** A memo, a decision tree, a sample pipeline with an evaluation?
- **"How much time?"** The listing gives none. Ask, and scope to what you can check in that time.

## Answer

### Words you need first

- **Eval.** Short for evaluation: a set of real inputs with the right answer or a pass/fail rule for each, run
  against the model to get a score. It is the AI version of a test suite.
- **Prompt engineering.** Improving the instructions and examples you send with every request, without training.
- **Deprecation.** The provider announces a model will stop working on a date. Fine-tunes built on it stop too.

### What the docs say today (fetched 2026-10-12)

**The recommended order.** The optimization guide frames the workflow as evals first, then prompt engineering,
then fine-tuning, and says the prompt engineering process "may be all you need".

**Four methods,** each needing different data:

| Method | What you train on | What it is for |
|---|---|---|
| Supervised fine-tuning (SFT) | Input and ideal-output pairs | Format, classification and instruction-following failures |
| Vision fine-tuning | Examples that include images | Tasks with image inputs |
| DPO (direct preference optimization) | Pairs of answers, one preferred and one not | Tone and focus |
| Reinforcement fine-tuning (RFT) | Tasks an expert can grade | Reasoning tasks; reasoning models only |

**The wind-down.** The guide also says: "OpenAI is winding down the fine-tuning platform. The platform is no longer
accessible to new users." The deprecations page gives the dates
([OpenAI deprecations](https://developers.openai.com/api/docs/deprecations)):

| Date | What changes |
|---|---|
| May 7, 2026 | No new jobs for organizations that haven't fine-tuned before |
| July 2, 2026 | No new jobs for organizations without fine-tuned-model use in the past 60 days |
| Oct 23, 2026 | Fine-tuned GPT-3.5, GPT-4, GPT-4.1-nano and o4-mini models listed for shutdown |
| Jan 6, 2027 | No new jobs for active existing customers |
| Until base deprecation | Existing fine-tuned models keep answering requests |

If the take-home predates these changes, say you are answering for the docs as they now stand, and give the date
you read them.

Say it like this: "The first thing the docs tell me is that the platform is closing, so half the strategy is
migration."

### A customer-facing strategy

Follow one customer through it. Say a company runs a fine-tuned GPT-4.1-nano that sorts support tickets, and it is
listed for shutdown on Oct 23, 2026.

1. **Eval first, prompt second.** Most teams should never reach fine-tuning. For new work, build the eval and try
   prompting before anything else.
2. **Pick the method from the data you have.** Input and output pairs point to SFT. Preferred and rejected pairs
   point to DPO. A reasoning task that experts can grade consistently points to RFT.
3. **Inventory existing fine-tunes.** For each: its base model, its shutdown date, its traffic and its eval set.
   The ticket sorter's deadline is Oct 23.
4. **Pick a migration path for each.** Either a newer base model with a better prompt (re-run the eval), or an
   open-weight model with **LoRA** hosted elsewhere. LoRA (low-rank adaptation) freezes the base model and trains a
   small add-on, tens of megabytes in size, that you can host with several providers.
5. **Gate every swap** on the same held-out eval (examples the new model never trained on), comparing old and new
   on the same items.

For the ticket sorter, the cheapest outcome is that a newer model with a good prompt passes the same eval. Only if
it doesn't is a LoRA migration worth pricing.

### A product-strategy reading

If the audience is OpenAI, explain the trade-off from the provider's side as hypotheses, not facts. Every fine-tune
pins a base model the provider must keep serving. Stronger base models with longer context (they can read more text at once) reduce how often
customers need one. Don't present a reason OpenAI hasn't stated.

Say it like this: "Here is what the docs state, and separately, here is my guess at why. I'd label the second part
as a guess."

## Small-team version

If your company has fine-tunes on a closed provider, this is an operations task, not an essay:

1. List them, with each base model's shutdown date.
2. Re-run your eval on the replacement model with your best prompt. This is the cheapest outcome, so try it first.
3. Where a fine-tune still pays, move to a LoRA adapter on an open model you can host on more than one provider.
   Accept that you now own serving.

The prices show where the decision really sits. Re-training an 8-billion-parameter LoRA costs about **$4**. Serving
it on a dedicated GPU costs about **$4,010 a month**. Serving, not training, decides whether the migration is worth
it.

<summary>The arithmetic behind the numbers (for a Staff-level follow-up)</summary>

- **Training:** 2,000 examples × 1,000 tokens × 3 epochs (passes over the data) = 6M tokens × $0.34 per 1M ≈ $2,
  billed at the **$4** job minimum. A token is a piece of text about ¾ of a word.
- **Serving:** one dedicated H100 GPU at $5.49 per hour × 730 hours ≈ **$4,010 a month**.

## Pitfalls

- **Writing from memory.** The platform changed in 2026; read the current docs and date them.
- **Recommending fine-tuning without an eval first.** Most teams don't need it, and you can't show that without a
  score.
- **Ignoring base-model deprecation.** It ends every fine-tune eventually, so shutdown dates are deadlines.
- **Stating OpenAI's motives as facts.** Label inference as inference.
