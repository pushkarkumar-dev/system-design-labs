## What they're really asking

> **If you only remember one thing, say this in the first minute:**
> "I'll say the approach and its complexity before I type, so the suggestions are completing my plan instead of
> choosing it. I'll accept suggestions a line or a block at a time, read each one first, and when one is wrong I'll
> say what's wrong before I fix it. I'll use the chat for test cases, and run the tests as I go. With help
> available I expect the bar to be a bit higher, so I'll aim to finish with time for a follow-up."
>
> The rest of this page explains each part of that answer.

The question underneath: does autocomplete-style help make you better, or sloppier?

In a normal coding round, everything on your screen came from your head. Here an assistant suggests code as you
type. GitHub Copilot is backed by a **large language model (LLM)**: a program trained on huge amounts of text and
code that predicts plausible next code from what is already on the screen. "Plausible" means "common". So a
suggestion tends to steer you toward the most common solution, which may not be the one this problem needs, and
it can be subtly wrong in ways that look right. Because you share your screen, the interviewer watches every
suggestion you accept. Your review habits are on display.

A Microsoft CoreAI SDE (software engineer) candidate wrote before the onsite that one round needed "an IDE
connected to an AI coding assistant" (<Cite id="s-9766c0f8b8" />); Blind search previews describe VS Code with
GitHub Copilot while sharing your screen (<Cite id="s-3cb1673d3e" />). A commenter called it "similar difficulty
to their standard coding rounds" with "a slightly higher bar since you have help", and advised "Review every
suggestion before accepting" (<Cite id="s-02f49004af" />). Confidence is low: no official description exists, and
the policy appears to vary by team.

## Clarify first

- **Which assistant features are allowed?** Inline completion only, chat, or agent mode?
- **Is the problem algorithmic, or in an existing project?** Assume a standard coding problem.
- **Will the interviewer watch the whole screen, including the chat panel?** Assume yes, so narrate.
- **May I run code and tests in the IDE?**

## Answer

### Words you need first

- **Inline completion**: grey suggested text that appears ahead of your cursor as you type. One key (Tab) accepts
  it.
- **Chat panel**: a side window where you ask the assistant questions in plain language.
- **Agent mode**: the assistant edits files and runs commands on its own. Ask whether it is allowed; usually the
  round is about the first two.

### State the approach before the first keystroke

Say the algorithm and its complexity out loud, then start typing. Inline completion is fastest when it is
completing what you already decided. Without a plan, it chooses for you.

### The worked example: merging intervals with suggestions on

Assume the problem is "merge overlapping intervals", a standard coding question (an illustration; the reports
don't name the problem). You say the plan first: "Sort by start, then walk once, extending the last merged interval
when the next one overlaps. O(n log n) for the sort." Then you type, and suggestions appear:

| You type | The grey suggestion | Your call | What to say in the interview |
|---|---|---|---|
| `def merge(intervals):` | the whole function, 12 lines | reject the whole block | "I'll take it a few lines at a time so I can read each one." |
| `intervals.sort(` | `key=lambda x: x[0])` | accept | "Sort by start, as planned." |
| `for s, e in intervals:` then `if merged and merged[-1][1]` | ` > s:` | **reject** | "Strictly greater than misses touching intervals like [1, 2] and [2, 3]. The spec says those merge, so it's `>=`." |
| the extend line | `merged[-1][1] = e` | **reject** | "That shrinks the interval when the new one is inside it. It must be `max(merged[-1][1], e)`." |
| `else:` | `merged.append([s, e])` | accept | "New interval starts a new group." |

Two of the five suggestions were wrong, and both looked right at a glance. Saying why out loud, before fixing, is
what turns this from "the candidate typed slowly" into "the candidate caught two bugs".

Then use the chat for the checkable work: "Give me edge-case tests for merge intervals." Expect cases like an empty
list, one interval, touching intervals, one interval inside another, and unsorted input. Run them.

### Treat each suggestion as a pull request

Read every grey suggestion before accepting it. Accept in small chunks, a line or a block, not a whole function you
haven't read. When a suggestion is wrong, say why before you fix it: "this loop runs one index too far and would read
past the end", "this sorts inside the loop, O(n² log n)". The commenter's advice above is exactly this, and the interviewer
sees it on your screen.

Say it like this: "I read each suggestion like a pull request: does it match the plan, and what input would break
it?"

### Use chat for the checkable work

Ask for test cases, especially edge cases, and for an explanation of any library call you're unsure of. Then run
the tests. Don't ask the chat to pick the algorithm; that is the part being graded.

### When the suggestion is better than your plan

Sometimes the grey text is better than what you were about to type: a library function you forgot, or a cleaner
loop. Accept it, and say why, so the interviewer sees a decision rather than a reflex: "That's `bisect_left` from
the standard library; it does the binary search I was about to write, and I know its edge cases." The rule is not
"reject suggestions". The rule is that nothing goes in that you can't explain. A suggestion you can explain is as
good as code you typed, and faster.

### Higher bar, same problem

If help is available, the interviewer may expect a cleaner solution, more tests, or a follow-up done in the time.
Budget for that by not over-discussing the easy parts. Use the saved minutes on what shows judgment: complexity
trade-offs, failure cases, what changes at scale.

## Small-team version

Inline completion is the cheapest AI tool a small team has, usually a per-seat subscription. The riskiest habit
that comes with it is pressing Tab on code nobody read.

- **Make review explicit in the workflow.** Tests in CI, linters and the race detector on every change, and small
  pull requests so a reviewer actually reads them.
- **Measure whether it helps.** If review time or bug reports rise after adoption, the team is accepting too much
  unread code. Both are numbers you already have in your issue tracker and code host.
- **Keep the plan-first habit.** For any change beyond a few lines, write the approach in the PR description first.
  It makes the completion follow your design, and it gives the reviewer something to check the code against.

## Pitfalls

- **Accepting a whole generated function, then debugging it live.** You spend the round reading code you didn't
  plan.
- **Letting the suggestion choose the algorithm.** It suggests the common solution, not necessarily the right one.
- **Silent screen time.** The interviewer can see you reading; say what you see.
- **Fixing a wrong suggestion without saying what was wrong.** The catch only counts if the interviewer hears it.
