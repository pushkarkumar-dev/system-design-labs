## What they're really asking

> **If you only remember one thing, say this in the first minute:**
> "I'd release in stages, with a gate between each stage. Before anyone outside sees it, the new model must be no
> worse than the old one on our task tests and on every harm area, and serious red-team findings must be fixed.
> Then internal users, trusted testers, a percentage rollout and finally everyone. Any threshold missed, any tester
> concern we can't explain, or an untested rollback blocks the release. And one named person signs the release and
> the list of risks we're accepting."
>
> The rest of this page explains each part of that answer, so you can say it with understanding.

The question, as Hello Interview's OpenAI guide lists it, is "If you were in charge of deciding whether to release a
new AI model, what criteria would you use to make that decision?". It sits alongside a question about AI-safety
implications in your own work (<Cite id="s-4d55d9b987" />).

The interviewer wants to know whether you can own a release decision when you can't be sure: define the gates, the
owners, the stages, the signals that block, and the risk you accept. The Staff signal is a decision procedure you
would defend, not a list of things that matter.

### What makes this different from a normal release

You already know how to release a service: tests pass, canary, watch the dashboards, roll back if errors rise.
That carries over. Three things change with a model.

1. **Tests give percentages, not green or red.** A **large language model (LLM)** is a program that reads and
   writes text, and it can answer the same question differently each time. So you test it with an **eval**: a
   fixed set of test inputs plus a scoring rule, run against every version. Two versions are compared by score,
   and small differences can be noise.
2. **The failures are behaviors.** A worse model doesn't crash. It gives dangerous advice, leaks data, or
   flatters users. You need a separate **harm eval** for each **policy area** (a category of harm, such as
   self-harm or weapons).
3. **Users can like the wrong thing.** Positive feedback is not a safety signal. The best-known case, covered
   below, is a model update users rated well that was rolled back within days.

## Clarify first

The gates depend on the release, so ask:

- "A new model behind an existing product, or a new public model?" The gates differ in scope.
- "Who are the users, and through what surface: API, consumer app, enterprise?"
- "Is this a frontier model where dangerous-capability thresholds apply, or a task model?" A **frontier model** is
  one of the most capable models in the industry, where the question is also what new dangerous things it can do.
- "Who has authority to block, and is that me in this scenario?"

## Answer

### The release, as a pipeline

Picture the release as a series of stages with a gate between each one:

```
New model version
   │  Gate 1: quality and harm evals no worse than the current model
   │  Gate 2: red-team findings triaged; capability thresholds checked;
   │          policy and legal sign-off
   ▼
Internal use ── employees only
   │  Gate 3: no unexplained reports
   ▼
Trusted testers ── a small outside group
   │  Gate 4: tester concerns explained or fixed
   ▼
Percentage rollout ── 1% → 10% → 50%, behind a feature flag
   │  Gate 5: live monitoring within limits; rollback exercised
   ▼
General availability
```

Each stage has an exit criterion and a rollback trigger. **Red-teaming** means people deliberately trying to make
the model misbehave before release, like a penetration test. A **rollback** that has never been exercised is a
plan, not a capability.

### The gates

1. **Quality.** At least matches the previous model on the task evals that matter to users, with confidence
   intervals (the range the true score probably falls in), not a single number.
2. **Harm evals per policy area.** No regression against the previous model; thresholds set before the run.
3. **Red-team findings.** Triaged by severity; high-severity ones fixed or mitigated, the rest written down as
   accepted risk.
4. **Capability thresholds.** For frontier models, evaluations against the company's published framework.
   Anthropic's Responsible Scaling Policy ties **capability thresholds** (levels of dangerous capability a model
   might reach) to required safeguards
   ([Anthropic RSP, version 3.4, effective 2026-07-08](https://www.anthropic.com/responsible-scaling-policy)).
   Read the interviewing company's own framework beforehand.
5. **Operational readiness.** Capacity, cost per request, monitoring, and a rollback that has been exercised.
6. **Policy and legal review.**

### One release, gate by gate

Here is one case, so you can hear the gates with values in them. Assume you own a homework-help chat assistant in a
consumer app, and the new model is the one behind it. Every number below is an illustrative assumption.

| Gate | Illustrative result | Decision | What to say in the interview |
|---|---|---|---|
| Quality | 86% vs 84% on 200 task items | Pass, as "no worse" | "That gap is inside the noise for 200 items, so I won't claim it's better." |
| Harm evals | One policy area slightly worse | Block | "We set the threshold before the run. A regression blocks until we know why." |
| Over-refusal | Many more refusals on chemistry homework | Fix before rollout | "Refusing honest students is a cost too. It goes on the same dashboard." |
| Red team | One high-severity way to get dangerous instructions out | Fix, then re-test | "High severity is fixed before any outside user sees it." |
| Testers | Two say it "agrees too easily" | Block | "Unexplained, so we build an eval for it first." |
| Rollout | Rollback tested in staging | Pass | "Now 1% for a day, with limits that trigger the rollback." |

**Over-refusal** means the model refuses a legitimate request because it looks a bit like a harmful one. It is the
AI version of a false positive.

### Blocking signals beyond the metrics

A credible qualitative report that no eval explains should block. OpenAI's April 2025 GPT-4o update is the case to
cite. It was rolled back for **sycophancy**: the model told users what they wanted to hear. Per a brief quoting
OpenAI's postmortem, there were no deployment evals for sycophancy, expert testers said the model "felt slightly
off", and it launched on positive user signals before being rolled back
([Georgetown Law brief](https://www.law.georgetown.edu/tech-institute/insights/tech-brief-ai-sycophancy-openai/), postmortem 2025-05-02).

The criterion that follows: an unexplained tester concern blocks until an eval measures it.

Say it like this: "If trusted testers say it feels off and our evals can't explain why, the evals are missing
something. I'd block until we've measured it. That's the GPT-4o lesson."

### Ownership

One named person signs the release and the list of accepted risks. Say who you'd want that to be and why.

Say it like this: "Every release accepts some leftover risk. I want those written down, with one person's name next
to the list, so nobody can say later that they didn't know."

## Senior vs Staff

<LevelContrast
  title="Release criteria"
  senior={["Lists quality, safety and operational gates with thresholds and a staged rollout."]}
  staff={["Defines who signs off on accepted risk, treats unexplained qualitative signals as blocking, and explains how a delay is communicated and what it costs."]}
/>

In plain terms: Senior builds a good checklist. Staff decides who can say no, what overrides good-looking
numbers, and how to tell the business that the date is moving.

## Small-team version

You are unlikely to release a model. But you release model swaps and prompt changes constantly, and each one is a
release. The **system prompt** (the instructions your product puts in front of every conversation) is code, and a
change to it can change behavior as much as a new model.

Use a one-page checklist: task evals versus the current version, the harm checks relevant to the feature, a
percentage rollout with a kill switch (a flag that turns the feature off), and a weekly read of real outputs
afterwards. Vendor model updates count too. Pin versions where the provider allows it, and re-run your evals before
moving.

Gating every change is affordable. A 200-item suite run 3 times on a feature that makes one model call is about
**$13 per run** at Claude Sonnet 5 list prices fetched 2026-10-11. Ten changes a week is about **$130**, or **$260**
if you re-run the baseline each time.

<details>
<summary>The arithmetic behind the numbers (for a Staff-level follow-up)</summary>

Token counts are assumptions from the [eval-system walkthrough](/system-design-labs/interviews/walkthroughs/eval-system/).
A **token** is a chunk of text of roughly ¾ of a word; model prices are per million tokens.

- **Feature runs:** 200 items × 3 trials = 600 runs at about 4,000 input and 400 output tokens on Claude Sonnet 5
  ($2 in, $10 out per million): 600 × (4,000 × $2 + 400 × $10) ÷ 10⁶ = **$7.20**.
- **Judges:** two pass/fail judge calls per run on Claude Haiku 4.5 ($1 in, $5 out per million), about 4,500 input
  and 50 output tokens each: 1,200 × (4,500 × $1 + 50 × $5) ÷ 10⁶ = **$5.70**.
- **Per run:** about **$13**; with the baseline re-run, about $26. Ten changes a week: **$130–260**.

## Pitfalls

- **Criteria with no thresholds or owners.** Nobody can block on an adjective.
- **Treating user approval metrics as a safety signal.** The GPT-4o rollback is the counter-example.
- **No staged rollout, or an untested rollback.** You find out it doesn't work during the incident.
- **Forgetting the cost of delay.** The answer then reads as "never ship", which isn't judgment either.
