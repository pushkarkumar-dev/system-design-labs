## What they're really asking

> **If you only remember one thing, say this in the first minute:**
> "I've used two assistants on real work: one daily for about six months, the other for three weeks. The first
> handles changes across many packages better; the second plans before it edits, which makes review faster. Both
> once invented a config option that doesn't exist in our library version, so now I give them the right docs
> every time. My default is the first one, and I'd switch only if a trial on our own tickets showed a real
> difference, or if cost or data terms changed."
>
> The rest of this page explains each part of that answer, so you can say it with your own tools.

The interviewer wants to know one thing: have you used several tools seriously enough to have opinions that
come from real work?

This is different from comparing two databases or two queues, which you may have done before. With a database,
the vendor's documentation, benchmarks and your own load tests mostly agree. AI coding tools change every few
months, their marketing pages all claim the same things, and how well they work depends heavily on your own
codebase. So the only comparison worth hearing is one built from your own tasks, including where each tool
failed. Anyone can read a feature list; only you can say what happened on your tickets.

The question comes from PromptLayer's post, written from the interviewer's side. It gives the sample "What AI
coding assistants do you use? Can you compare Cursor, Windsurf, Zed, and Claude Code?", names "Boring textbook
answers" as a red flag, and says "A tinkerer will explain not just what worked, but what didn't."
(<Cite id="s-1205b0cc50" />). The post itself warns its questions "can age quickly", so the tool list is dated;
the test isn't.

### Words you need first

- A **large language model (LLM)** is a program trained on a huge amount of text and code that predicts what
  text should come next. Every coding assistant is built on one or more.
- An **AI coding assistant** uses an LLM to suggest or write code, in your editor, a chat window or your
  terminal. A **coding agent** goes further: it reads files, edits several, runs tests, and keeps going until it
  thinks it's done.
- **Context** is the text the model can see while it works: the files, instructions and docs it was given. How
  a tool chooses what to put in context is one of the biggest differences between tools.
- A **hallucination** is a confident answer that is false, such as an **invented API**: a function or option
  that looks real and doesn't exist.

## Clarify first

- **Which tools?** "Do you want the tools I use at work, or also ones I've tried on side projects?" Both, labelled.
- **Assistants or models?** "Coding assistants only, or the models underneath too?" PromptLayer also looks for
  opinions on open versus proprietary models and "specific use cases where they'd choose one model over
  another" (<Cite id="s-1205b0cc50" />). An **open model** is one whose files you can download and run on your
  own machines; a **proprietary model** is only available through the vendor's service.
- **Tools you haven't used.** If they name tools you haven't used, say so and compare the ones you have. "I
  haven't used Zed, so I won't guess. I can compare the two I use every week."

## Answer

### The example we will follow

This page follows one illustrative engineer, Sam: a backend engineer on a large Go monorepo. Sam has used
"Tool A" daily for about six months and "Tool B" for three weeks on new services. Use the shape, with your own
tools; the names are placeholders on purpose, because the tools change faster than this page.

### Compare on things that matter

Pick four or five things to compare, and give a specific observation per tool. Here is Sam's comparison:

| Compare on | What it means | Sam's observation (illustrative) | What to say in the interview |
|---|---|---|---|
| **Context handling** | How well it works across many files or a large repository | Tool A read the call sites first and handled a cross-package refactor; Tool B lost track past a few files | "A did the cross-package change; B stopped after a few files." |
| **Planning and control** | Does it propose a plan you approve before editing? Can you constrain it? | Tool B proposes a plan before editing | "B's plan step made review faster." |
| **Failure mode** | How it goes wrong: invented APIs, over-broad edits, giving up, looping | Both invented a config option that doesn't exist in the library version Sam uses | "Both made up the same kind of thing, so I changed what I give them." |
| **Checkability** | How easy it is to review: diffs, logs, tests it runs | Tool B's plan plus a small diff was easiest to check | "I pick the tool whose work I can check fastest." |
| **Cost and data terms** | What it costs at your usage, and whether your company's data rules allow it | Only Tool A was approved for the main repository | "Data terms decided half of this before quality did." |

The last row matters more than candidates expect. A tool your company's rules don't allow on its code is not an
option, however good it is.

### Give tasks, not adjectives

"Faster", "smarter" and "better at context" are adjectives. Interviewers want tasks. For each tool, give one task
where it was better and one where it failed. Sam's version: "Tool A handled a cross-package refactor well because
it read the call sites first; Tool B stopped after a few files. Both invented a config option that didn't exist
in our library version, so I now put the pinned docs in context." "Pinning the docs in context" means handing the
tool the right version's documentation every time, so it stops guessing.

### Say your default and what would make you switch

"I use Tool A for cross-package changes and Tool B for small new services. I'd switch if a measured difference
on our own tasks, a cost change or a data-terms change gave me a reason." Deciding on your own tasks rather than on
public benchmarks is the point to land. Public benchmarks measure someone else's code.

If they push on models rather than tools, the same rule holds. Say it like this: "I'd pick a model by running
our own examples through each one and comparing quality, speed, cost and data terms. A fixed set of our own
examples with known good answers is called an eval, and I trust it more than any leaderboard."

### Include the human side

How you work with the tool matters as much as which tool. Plan approval, tests written first, and a **rule
file** (a text file in the repository, often `AGENTS.md`, that the agent reads at the start of every task) that
grows after each mistake. Mitchell Hashimoto describes turning each agent mistake into an AGENTS.md rule or a
tool ([mitchellh.com, 2026-02-05](https://mitchellh.com/writing/my-ai-adoption-journey)). A comparison that
ends with "and here is how I work with whichever one I use" shows you understand the tool is half of it.

In plain words: a Senior answer compares tools for yourself. A Staff answer describes how you would choose for a
team, and when you would choose again.

## Small-team version

At a small company the person who owns AI often picks the team's tools. Show how you'd decide, as a process:

1. **A two-week trial on real tickets**, not demos.
2. **A short list of things to compare**, the five in the table above.
3. **A data-handling review**: which tool may see which code and data.
4. **A cost cap per seat.**
5. **A date to re-evaluate**, because the tools change every few months.

Price the API-billed agents with arithmetic, not a guess. These agents are billed by the **token**, a chunk of
text of roughly ¾ of a word. On the family walkthrough's assumptions, one engineer costs about **$3.12 a day,
roughly $69 a month**.

<details>
<summary>The arithmetic behind the numbers (for a Staff-level follow-up)</summary>

- **Assumed use per engineer per day:** 2M input tokens, of which 1.6M are **cache reads** (repeated text the
  provider bills at a lower price), and 200K output tokens.
- **Claude Sonnet 5 list prices, fetched 2026-10-11:** $2 per million input, $0.20 per million cached input, $10
  per million output.
- **Per day:** 0.4M × $2 + 1.6M × $0.20 + 0.2M × $10 = $0.80 + $0.32 + $2.00 = $3.12.
- **Per month:** $3.12 × 22 working days ≈ $69.

</details>

Pick one default tool unless the trial shows a measured difference on your own tickets. A second tool doubles the
data review and the spend tracking. Say it like this: "One tool by default, a second only when our own tickets
show it's worth the extra review."

## Pitfalls

- **Feature lists from marketing pages.** They are the "boring textbook answers" the interviewer flags, and
  every candidate can recite them.
- **Opinions on tools you've only tried once.** One try can't show how a tool fails, which is the most useful
  thing you could say.
- **No failure modes.** A comparison where everything works sounds like you haven't used either tool hard.
- **Ignoring cost and data terms.** In practice these often decide the choice before quality does.
