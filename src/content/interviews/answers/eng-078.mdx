## What they're really asking

> **If you only remember one thing, say this in the first minute:**
> "I pick models per task, not per company. For each task I start with the smallest, cheapest model that might
> pass, run our own test set on it, and move up only where it fails. I compare cost per completed task, not price
> per token, because the providers count tokens differently. Then I commit: as of this month, for this task I use
> this model, because it passed our test at this cost, and here is what would make me switch."
>
> The rest of this page explains each part of that answer.

The interviewer wants to know two things. Do you actually use these models yourself? And do your opinions come from
evidence rather than from a leaderboard you read?

This is unlike choosing a database or a cloud provider. Those choices last years, and the trade-offs are written
down. With **large language models (LLMs)**, providers ship new models every few months, prices move, and a model
that is best at one task can be mediocre at another. So a fixed ranking goes stale fast. What lasts is a method for
choosing, plus picks you can date and defend.

Two terms first. A **token** is the unit providers bill by, a chunk of text roughly ¾ of a word; you pay for tokens
in (the **prompt**) and tokens out (the **output**). An **eval** is a fixed set of test inputs for one task, with a
way to score the outputs: code checks, human labels, or another model acting as a grader.

The question comes from a PromptLayer post written from the interviewer's side (2025-07-11). Its sample is "Which
model provider do you lean on for creative writing? Claude, OpenAI, Gemini?", it says "Top models change daily", and
it lists "Boring textbook answers" as a red flag (<Cite id="s-1205b0cc50" />).

## Clarify first

- **Which tasks?** "What does the team build: support answers, extraction, code, agents, creative text?"
- **What constraints?** "Data terms, where data may be stored, latency targets, budget?"
- **Personal picks or a method?** "Do you want my current picks, or how I'd choose? I'll give both: the method, then
  dated picks."

## Answer

### Start with a method

1. **Group tasks by what a failure costs and how you can check the output.** Classification and extraction into a
   fixed schema can be checked with code. Answers grounded in documents need a grader or human labels. Agent runs
   (a model calling tools in a loop) need end-to-end task success.
2. **Start each task on the smallest tier that might pass.** Providers sell models in sizes: small, cheap and fast;
   large, expensive and better at hard tasks. Each size is a **tier**. Run the task's eval on the small tier and move
   up only where it fails.
3. **Price per task, not per token.** Each model has its own **tokenizer**, the rule that splits text into tokens, so
   the same text can be a different number of tokens. Anthropic's pricing page says Claude 4.7+ models produce about
   30% more tokens for the same text. Measure cost per completed task on your own prompts.
4. **Keep a second provider passing the eval** for each tier, as a fallback for outages and price changes.

Say: "The method outlives any ranking. The ranking changes every quarter."

### Why the method matters: the price spread

The gap between tiers is huge. As fetched 2026-10-11, Claude Haiku 5.5 output cost $0.50 per million tokens (prompts
up to 100K) and Claude Opus 5.5 $20: **40×**
([Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing)). OpenAI listed gpt-5-nano at $0.40
and gpt-5.5 at $30 per million output tokens ([OpenAI pricing](https://developers.openai.com/api/docs/pricing)).

A 40× price gap means picking the big model "to be safe" for a high-volume task can be the largest line in the
bill. Picking the small one without an eval can quietly ship worse answers.

### One worked example: is the cheap tier really cheaper?

Say you have a support-ticket tagging task. Two tiers pass different shares of your eval:

| Tier | Price (relative) | Eval success rate | Cost per *successful* task (relative) | What to say in the interview |
|---|---|---|---|---|
| Large | 1 | 90% | 1 ÷ 0.9 ≈ 1.11 | "The large tier is the baseline." |
| Small | 0.1 | 60% | 0.1 ÷ 0.6 ≈ 0.17 | "Even failing 40% of the time, the small tier is about 6.7× cheaper per success." |

The catch is in the last column's condition: that only holds **if failures are caught and retried**, for example by a
code check on the schema, rather than shipped to users. For a task you can check automatically, the small tier plus
a retry wins. For a task where a wrong answer reaches a customer unnoticed, the success rate matters more than the
price.

Say: "Cost per success is what I compare, and it only counts if I can catch the failures."

  your own prompts.

### Then give dated picks

Commit. A method with no picks sounds evasive. The shape of a good answer:

"As of this month, for ticket tagging I use model A, because it passed our eval at this cost per task. I tried B; it
failed on Y. For customer-facing answers I use C. I'd switch if D passes the same eval at half the cost."

Name what would make you switch. Only claim quality differences you have measured or can point to.

### Also cover

- **Embeddings** (lists of numbers that represent meaning, used for search): a dedicated embedding model, called in
  batches.
- **Offline work:** a **batch API**, where you submit requests that nobody is waiting for and collect answers within
  hours, is 50% off at the major providers per their pricing pages.
- **Open-weight models on serverless endpoints:** a provider runs a published open model and bills per token. Useful
  where data terms allow and price matters most.

## Senior vs Staff

<LevelContrast
  title="Model choice"
  senior={["Picks per task from a small eval, knows current prices, and can say why the last switch happened."]}
  staff={["Runs model choice as a process: an eval per task, a fallback per tier, a quarterly re-test, and cost per successful task as the decision metric."]}
/>

In plain words: a Senior answer has good, evidenced picks. A Staff answer turns picking into a routine the team
repeats, so the picks stay right after the author has moved on.

## Small-team version

Keep a one-page model table:

| Task | Current model | Fallback | Eval pass rate | Cost per task | Date checked |
|---|---|---|---|---|---|

Re-run the evals when a provider ships a new tier; an agent can run the sweep overnight. That is the whole process
for a small team, and it costs an afternoon a quarter.

Surveyed teams mostly route by task type (44%) rather than cost (11%)
([Amplify Partners 2026](https://amplifypartners.com/blog-posts/the-2026-ai-engineering-report)). Say: "We pick by
task, check it with an eval, and write the date next to it."

## Pitfalls

- **A leaderboard ranking with no task and no date.** It is exactly the "textbook answer" the interviewer is screening out.
- **Comparing price per token across different tokenizers.** Anthropic says Claude 4.7+ models produce about 30% more tokens for the same text.
- **Strong opinions with no evidence behind them.** An opinion is only worth as much as the eval behind it.
- **One model for everything.** You overpay on easy tasks or underperform on hard ones.
