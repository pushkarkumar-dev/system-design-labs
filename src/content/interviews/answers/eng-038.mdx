## What they're really asking

> **If you only remember one thing, say this in the first minute:**
> "Nothing, at first. 'Feels dumb' points me at conversations, not at a fix. I'd pull that customer's
> conversations and a sample of similar ones, read them, and label what went wrong in each. Then I'd group
> the labels into a few failure types and count them. I'd fix the most common or most costly one, which is
> often a bug in what context the bot receives or what it looks up, not in the wording of the prompt. Then
> I'd re-run the same conversations on the old and new versions to show the count went down, and keep the
> customer's examples as permanent tests."
>
> The rest of this page explains each part of that answer.

The interviewer wants to see whether your first move is to look at data or to edit the prompt. They want you
to turn a vague complaint into labelled failure cases you can count, pick the costliest one, fix it, and show
the number moved.

### What makes this different from a normal bug report

A normal bug report says "clicking Save throws a 500". You reproduce it, find the line, fix it.

"Feels dumb" about a bot built on a large language model (**LLM**) has no stack trace and no single cause:

1. **There is no error.** Every reply was produced successfully. The problem is in what the replies say.
2. **It's usually several problems at once.** "Dumb" bundles together forgetting what the user said, looking
   up the wrong document, and answering the wrong question.
3. **The obvious fix is often wrong.** Rewriting the instructions or switching to a bigger model feels like
   progress, but if the bot never received the information, no prompt will fix it.

So the first job is to find out what "dumb" means here, in numbers.

The prompt is the techinterview.org applied-AI guide's example for the product-sense round, which it
describes as "turning a fuzzy user problem into a scoped, measurable system" (<Cite id="s-7d03a572e0" />).

### Words you need first

- **Trace**: the full log of one conversation: what the user said, what the bot looked up, every tool call,
  and every reply. It's the LLM version of a request trace.
- **Error analysis**: reading traces and writing a short note on what went wrong in each. Writing those notes
  is called **annotating**.
- **Failure mode**: a named, recurring kind of failure that you can count, such as "asked for information
  the user already gave".
- **Eval set** (or **golden set**): a fixed list of test conversations, each with checks for a good outcome.

## Clarify first

- **Which customer, which conversations, since when?** "Did anything change recently? A recent change is my
  first suspect."
- **What did they expect?** "Dumb" often means it didn't use something it should have known.
- **One customer or many?** Check complaint volume and the thumbs-down trend.
- **Do we have traces?** "Do we log what the bot looked up and which tools it called? If not, that's the
  first fix."

## Answer

### Step 1: change nothing yet; read

Pull that customer's conversations plus a sample of similar ones (say 50–100) and read them. Hamel Husain
and Shreya Shankar's evals FAQ recommends annotating at least 30 traces yourself with open-ended notes, then
grouping the notes into failure modes, and continuing until new traces stop showing new ones
([FAQ](https://hamel.dev/blog/posts/evals-faq/), modified 2026-09-21).

Typical failure modes behind "dumb":

1. **Ignores context the user already gave.** It asks for the order number twice.
2. **Looked up the wrong thing.** The search step returned a stale or wrong document, so the bot gave a
   confident wrong answer.
3. **Refuses or hands off something it could answer.**
4. **Answers a different question.**
5. **Wordy, generic tone.**

Say: "Before I touch the prompt, I read the conversations and label what went wrong in each one."

### Step 2: count, and follow one example

Say you read 60 traces. Here is how the investigation goes:

| Step | What you find or do | What to say in the interview |
|---|---|---|
| Read 60 traces | Mode 1 (ignores context) in 18 of them. Mode 2 (wrong document) in 11. | "Two modes explain most of the complaint." |
| Pick the top mode | Mode 1, 18 of 60. | "Most frequent first, unless a rarer one is much more expensive." |
| Make it a check | Code check: did the bot ask for a field already present in the conversation? | "Code where possible; it's cheap and never disagrees with itself." |
| Find the cause | The conversation history isn't being passed to the model after a handoff. | "This is a context bug, not a prompt problem." |
| Fix and re-run | Old and new versions on the same 60 traces: mode 1 drops from 18 to 3. | "Same items, before and after; that's a clear signal even on 60 items." |
| Make it permanent | The 60 traces join the test set. | "The customer's examples are now regression tests." |

For modes that code can't check, such as "answered a different question", use an **LLM judge**: a second
model call that grades the reply against one written rule and returns pass or fail. Check its verdicts
against your own labels before you trust it.

### Step 3: fix the biggest, then measure

The fix depends on the mode, and usually it isn't the prompt:

- **Mode 1** is usually a context-assembly bug: the conversation state isn't passed to the model.
- **Mode 2** is a retrieval or freshness problem: the search index is stale, or the search step ranks the
  wrong document first.

Compare the old and new versions on the same items. This is a **paired comparison**: you look at which
items flip from fail to pass. A fix that moves 18 failures to 3 on the same items is a clear signal even on
60 items. A 2-point change in an average is not.

<details>
<summary>Why 18 → 3 on 60 items is convincing and a 2-point change is not (for a Staff-level follow-up)</summary>

On the same 60 items, 15 failures turned into passes. If the fix did nothing, you would expect fails to flip
to passes and passes to flip to fails about equally often, by chance. Fifteen flips one way and none or
almost none the other is far outside that. A 2-point average change on 60 items is about one item, which
chance alone produces all the time. For scale, a single pass rate of 85% on 50 items has an error bar of
about ±9.9 points (the family walkthrough's back-of-envelope).

</details>

### Step 4: tell the customer

Tell them what you found, what changed, and that their examples are now permanent regression tests.

Say: "Here's what was going wrong, here's the before-and-after count, and your examples now run on every
change we make."

## Small-team version

This is a half-day job for one engineer. Use a notebook or a small annotation screen an agent builds, 50–100
traces, and a spreadsheet of failure modes. No vendor needed.

- **Time:** at an assumed 2 minutes a trace, 60–100 traces is **2–3.3 hours** of reading (120–200 minutes).
- **Money:** re-running 60 items on two versions costs **a few dollars** in tokens (the chunks of text that
  providers bill for): 120 runs at about 1.2 cents for a single model call, up to about 5 cents for a
  multi-call agent conversation (the family walkthrough's assumed token counts and Claude Sonnet 5 list prices).

What you must not hand off is the reading. An agent can search for similar traces after you have labelled
the first 30, as the FAQ suggests.

## Pitfalls

- **Rewriting the system prompt before reading a single trace.** You don't yet know what is broken.
- **Switching to a bigger model as the first fix.** A bigger model can't use context it never received.
- **Fixing the anecdote without adding it to the eval set.** It will come back with the next change.
- **Reporting "it feels better now".** Replace one feeling with another and nobody can check it; show the
  count.
