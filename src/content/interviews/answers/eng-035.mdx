## What they're really asking

> **If you only remember one thing, say this in the first minute:**
> "I'd use three layers. First, code checks that block any draft missing a required disclosure, containing a
> banned claim, or with an amount that doesn't match our records. Second, a person approves every draft at
> launch, and their edits and rejections become my test set. Third, every prompt or model change must pass
> an offline test suite before release. A category of message only earns automatic sending after about
> 3,000 clean reviews in a row, which is what it takes to show a 1-in-1,000 defect budget. And one named
> owner signs off every release."
>
> The rest of this page explains each part of that answer.

The interviewer wants to know whether you treat human review as a **release control** with a budget and an
owner, not as a vague "human in the loop". The prompt spells out what to cover: "Say what blocks an unsafe
send, who is accountable when one slips through, and what your failure budget is"
(<Cite id="s-a982325743" />). It is a practice prompt from an Anthropic prep guide for forward-deployed
engineers (engineers who build AI features alongside a customer's team), not a candidate report. The interviewer wants numbers attached to all three parts.

### What makes this different from a normal outbound-message system

A normal system that sends customer notices fills a template. You test the template once, and every message
it produces is predictable.

An **agent** that drafts messages is different. Here an agent means a program that uses a large language
model (**LLM**) to write text and call tools, such as looking up an account. Its output is new text every
time:

1. **Every draft is different**, so you can't approve the template once and trust every message.
2. **Mistakes are quiet.** A missing disclosure or a wrong date doesn't throw an error. It just gets sent.
3. **In a regulated industry a single bad message is a compliance event**, not a bug report.

So you need checks on every message, people in the loop until the data says they can step back, and a
number that says when "step back" is safe.

### Words you need first

- **Defect**: a message that breaks a rule. Here: a missing disclosure, a wrong amount or date, a prohibited
  promise, or personal data sent to the wrong person.
- **Failure budget**: the highest defect rate you will accept, agreed with compliance. This page assumes 1
  defect per 1,000 sent messages.
- **Eval set** (or **golden set**): a fixed list of test cases, each with what a good output must contain.
- **LLM judge**: a second model call that grades a draft against one written rule and returns pass or fail.

## Clarify first

- **Which regulation, and which messages?** "Let's assume a lender's collections or account notices, where
  required disclosures and prohibited claims are written down."
- **What counts as a defect?** "I'll use: missing disclosure, wrong amount or date, a prohibited promise,
  personal data to the wrong person."
- **What failure budget will compliance accept?** "I'll assume 1 defect per 1,000 sent messages."
  (assumption)
- **Who sends today, and how long does review take?** That is the baseline cost the agent must reduce.
- **What must be kept for audit?** Every draft, check result and approver, usually.

## Answer

### The three layers, as a picture

```
Agent writes a draft
   │
   ▼
Layer 1: code blockers ── disclosure present? banned phrase? amounts and dates
   │                      match the system of record? right recipient?
   │      fail → goes to a person with the reason
   ▼
Layer 2: human approval by risk tier ── sent unchanged / edited / rejected (logged)
   │
   ▼
Message sent, and recorded in the audit log
   │
   └──► edits and rejections become test items for Layer 3

Layer 3 (on every prompt or model change): offline test suite ── must pass before release
```

**Layer 1: code blockers before any send.** These are plain code, not AI. Check that required disclosures
are present and prohibited phrases are absent. Check every amount, date and account reference against the
system of record. Check the recipient matches the account. A blocked draft goes to a person with the reason.
Code is the right tool because these rules are written down and never need judgment.

**Layer 2: people approve by risk tier.** At launch a reviewer approves every draft. The review tool records
whether the draft was sent unchanged, edited or rejected. That record is valuable: it is your **label set**,
the human verdicts you test everything else against. Edits and rejections become test items and new failure
modes.

**Layer 3: offline evals gate every change.** Build a golden set from those reviewed drafts. Grade it with
code checks plus one **calibrated** LLM judge per open-ended failure mode. Calibrated means you have measured
how often the judge agrees with your reviewers' labels. Open-ended modes include tone that implies a threat,
or a claim the policy doesn't support. Compare each candidate prompt or model against the current one on the
same items. Keep must-pass items for every past compliance defect: one failure blocks the release.

Say: "Code blocks what is written down. People handle judgment. The test suite stops a change from undoing
either."

### Follow one category to auto-send

Take one category: payment-reminder notices. Follow it from launch to automatic sending.

| Stage | What happens | What to say in the interview |
|---|---|---|
| Launch | Every draft passes Layer 1, then a reviewer approves it. | "At launch, nothing goes out without a person." |
| Collecting evidence | Each approved draft with no defect counts toward the bar. | "I'm measuring this category's defect rate, not the whole system's." |
| The bar | About **3,000 reviewed drafts in a row with no defect**. | "That's what it takes to show a 1-in-1,000 budget at 95% confidence." |
| A defect appears at draft 1,800 | The count hasn't shown the budget yet. Add the case as a test item and keep reviewing. | "One defect in those 3,000 means we haven't shown the budget." |
| Auto-send | Layer 1 still runs on every message. A fixed sample (say 2%, assumed) is still reviewed. | "Sampling keeps the defect rate measured after we step back." |
| Any later defect | The category drops back to full review. | "Trust is earned per category and lost on one defect." |

Why 3,000? If the true defect rate were as high as 1 in 1,000, seeing 3,000 clean drafts in a row would
happen less than 5% of the time. So 3,000 clean drafts let you say, with 95% confidence, that the rate is
below the budget.

### Accountability

A named owner signs off every release of the prompt, the model and the test suite. An audit log keeps each
draft, the check results, the approver and the final text.

When a defect escapes, walk the chain: which layer should have caught it, why it didn't, and the test item
you add so it can't pass again. Then re-run the suite.

Tribunals have treated the bot as the company. In Moffatt v. Air Canada (2024) a Canadian tribunal held
the airline responsible for its chatbot's advice ([Law360](https://www.law360.ca/ca/articles/1804075)).

Say: "The accountable party is a named release owner, never 'the model'."

## Small-team version

- **Build** the blockers and the review queue yourself. The review screen is a small internal tool an agent
  can build quickly, and its edit/reject log is your best dataset.
- **Buy** nothing special. Reuse the tracing you have.
- **Spend** on compliance-reviewer time.

The money is in review time, not tokens. At 3,000 reviews per category and an assumed minute per review,
that is **about 50 reviewer-hours per category**. The agent's tokens for those 3,000 drafts cost **about $27**.
(A **token** is a chunk of text, roughly ¾ of a word; providers bill per token.)

<details>
<summary>The arithmetic behind the numbers (for a Staff-level follow-up)</summary>

- Review time: 3,000 reviews × 1 minute (assumed) = 3,000 minutes, about 50 hours.
- Tokens: say 3,000 input and 300 output tokens per draft on Claude Sonnet 5 at $2 / $10 per million (fetched
  2026-10-11): 3,000 × (3,000 × $2 + 300 × $10) ÷ 10⁶ = $27.

</details>

Review throughput, not tokens, sets the pace. Revisit when volume makes full review the bottleneck, or a
regulator asks for documented sampling.

## Pitfalls

- **"A human reviews it" with no numbers.** Without a budget, a sampling rate and an owner, review is a
  feeling, not a control.
- **Letting reviewers' edits vanish.** Every edit is a labelled example; throwing it away wastes your best
  data.
- **Auto-sending on a few hundred clean reviews.** A few hundred clean drafts can't show a 1-in-1,000 budget.
- **An LLM judge as the only blocker for a written rule.** If code can check it, code should block it; a
  judge can be wrong.
