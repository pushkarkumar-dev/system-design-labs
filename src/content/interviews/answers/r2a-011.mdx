## What they're really asking

## Answer

### Words you need first

- **LLM** (large language model). A program that reads text and writes text, built from billions of learned
  numbers called **weights** or **parameters**.
- **Token.** Models read and write text in pieces called tokens, roughly ¾ of a word. Each has an id.
- **bf16.** A 2-byte number format that most models use for their weights.

One running example ties the first three answers together: Llama-3.1-8B, an open model with about 8 billion
parameters. Using one public model makes every number checkable.

### 1. Fine-tuning (about two minutes)

**Fine-tuning** trains a model further on your own examples. **Supervised fine-tuning (SFT)** uses pairs of an input
and the ideal output, and scores the model only on the output tokens.

**LoRA** (low-rank adaptation) is the cheap way to do it. It freezes the original weights and trains a small add-on
for each adapted matrix: two thin matrices whose product `B·A` is added to the original. For Llama-3.1-8B at rank 16
on the four attention matrices, that is about **13.6 million parameters, about 27.3 MB**.

Use it for behaviour and format, after better prompts fail on a test set. Don't use it to add facts.

Say it like this: "LoRA trains a small change to a big model, about 27 megabytes here, so one base model can carry many of
them."

### 2. Token embeddings

The model's first step is to turn each token id into a vector (a list of numbers). It does this with a lookup
table, one learned vector per entry in the vocabulary. Llama-3.1-8B's table is 128,256 entries × 4,096 numbers =
**525 million parameters, about 1.05 GB** in bf16.

This is not the same as a **sentence-embedding model**, the kind used for search. That one turns a whole passage
into a single vector, so similar passages land close together.

### 3. The KV cache

The model writes one token at a time. In every layer, each token produces a **key** (what it contains) and a
**value** (what it passes on), and each new token has to look at the keys and values of all earlier tokens. Instead
of recomputing them for every new token, the model saves them in GPU memory. That store is the **KV cache**.

For Llama-3.1-8B it is **128 KiB per token**, so one 8,192-token request holds about **1.07 GB**. That memory, more
than the weights, limits how many long requests one GPU serves at once.

<details>
<summary>The arithmetic behind the numbers (for a Staff-level follow-up)</summary>

- **Embeddings:** 128,256 × 4,096 = 525,336,576 parameters × 2 bytes ≈ 1.05 GB.
- **KV cache per token:** `2 × layers × n_kv_heads × head_dim × bytes` = 2 × 32 × 8 × 128 × 2 = 131,072 B (128 KiB).
  The 2 is one key and one value. Llama-3.1-8B shares 8 key/value heads among its 32 query heads (grouped-query
  attention), which is why the formula uses KV heads. × 8,192 tokens = 1,073,741,824 B ≈ 1.07 GB.
- **LoRA:** per layer, r × (d_in + d_out) summed over q (4,096 → 4,096), k and v (4,096 → 1,024) and o
  (4,096 → 4,096) = 16 × 26,624 = 425,984; × 32 layers ≈ 13.6M parameters × 2 bytes ≈ 27.3 MB.

</details>

### 4. Evaluating RAG

**RAG** (retrieval-augmented generation) means looking up relevant passages from your documents and putting them in
the prompt before the model answers. It can fail in two places, so score them separately:

- **Retrieval: did we find the right passage?** Measure **hit@k**, the share of questions where a correct passage is
  in the top k results, or **recall@k**, the share of all correct passages found in the top k. Both need labelled
  question-to-passage pairs.
- **Generation: did the model use it well?** Is each claim supported by the retrieved text? Are citations correct?
  Does it decline when nothing relevant was found?

Report ranges, not single numbers. At about 300 questions, gaps of a few points are noise. In the rag lab, hit@3 on

### 5. The hash table

Say which design you'll use and why. **Separate chaining** is simplest: an array of buckets, each a small list.
**Open addressing** stores entries directly in the array and probes for the next free slot.

With chaining:

- **Put:** compute `hash(key) % capacity`, then replace the key in that bucket if it's there, or append it.
- **Get:** the same index, then scan the bucket.
- **Delete:** remove from the bucket. (With open addressing you'd leave a marker, a "tombstone", so later probes
  don't stop early.)
- **Resize:** when size ÷ capacity passes a **load factor** such as 0.75, double the array and rehash every entry.
  This keeps operations O(1) on average over time (amortized).

Mention that the worst case is O(n) if many keys hash to the same bucket. Test: insert, overwrite, delete, and many
keys across a resize.

## Small-team version

This breadth is the job description at a small company. The same person sizes a self-hosted model's memory,
decides whether to fine-tune, and builds the RAG evaluation.

Build the RAG evaluation first: a labelled set of 50–200 real questions with their source passages, run in CI. It
costs about **$2 a run** for 200 questions, so cost is not a reason to skip it. The real cost is the time to label
them.

## Pitfalls

- **Confusing token embeddings with sentence embeddings.** One is a lookup table inside the model; the other is a
  search tool.
- **The hidden-size KV formula.** It ignores shared KV heads and overstates the cache, 8× for Llama-3.1-70B.
- **One number for "RAG quality".** Score retrieval and generation separately.
- **A hash table with no resize.** It slows to O(n) as it fills.
