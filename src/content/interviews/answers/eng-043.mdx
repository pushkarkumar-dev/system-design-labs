## What they're really asking

> **If you only remember one thing, say this in the first minute:**
> "I evaluate an LLM system with three loops that feed each other. Automated tests run on every change: a
> test set built from real traffic, graded by code checks first and by AI graders that I've checked against
> people second, comparing the new version with the old on the same items. Human review runs on a cadence:
> a domain expert reads a sample of real conversations each week and labels new kinds of failure. Production
> feedback runs all the time: traces, user signals, and canaries for big changes. Every production failure
> becomes a test, and every human label keeps the AI graders honest."
>
> The rest of this page explains each part of that answer.

The interviewer wants a structured answer that covers all three loops (automated, human, production
feedback), says what each is for, and shows how they feed each other.

### What makes this different from testing normal software

For normal software, automated tests do almost all the work. They're exact and repeatable, and if they pass,
you're fairly confident.

A system built on a large language model (**LLM**) needs more than that, for three reasons:

1. **Output is random and open-ended.** The same input can get different answers, and many answers can be
   right. Automated grading needs judgment, and judgment can be wrong.
2. **The automated graders need checking.** If an AI grades your AI, someone has to check the grader. That's
   what the human loop is for.
3. **Tests go stale.** Users ask new things. A test set that never learns from production stops predicting
   production.

So no single loop is enough. Each covers a blind spot of the others.

A first-hand account of an OpenAI technical deep dive for a forward-deployed engineer (an engineer who
builds AI features alongside a customer's team) says the interviewer "pushed hard on
evaluation" with "How do you know your AI system is actually working well?", and that the candidate's answer
combined automated metrics, human evaluation and feedback loops (<Cite id="s-812dbc9385" />). The
candidate's reading is that interviewers use the question as a differentiator because most engineers
hand-wave it.

### Words you need first

- **Golden set**: a fixed list of test cases (**items**) built from real traffic, each with checks for a good
  outcome.
- **Trace**: the full log of one request: the input, what was looked up, every model and tool call, and the
  output.
- **LLM judge**: a second model call that grades an output against one written rule, returning pass or fail.
- **True-positive rate (TPR)** and **true-negative rate (TNR)**: how often a judge agrees with people. TPR is
  the share of real failures (as people labelled them) that the judge also fails. TNR is the share of good
  outputs that the judge also passes.

## Clarify first

- **What system?** A single model call over documents, or a multi-step agent? "Agents need step-by-step
  traces and a consistency measure across repeated runs."
- **What decision does evaluation drive?** Release gating, model choice, or monitoring.
- **What ground truth exists, and who can label?**
- **Traffic volume?** It decides how much live testing can measure.

## Answer

Use three levels, in Hamel Husain's 2024 framing: unit tests on every change, human and model evaluation on a
cadence, A/B tests after major changes ([Hamel Husain](https://hamel.dev/blog/posts/evals/), 2024-03-29).

### The three loops, as a picture

```
A change (prompt, model or setting)
   │
   ▼
1. Automated tests ── every change: golden set, code checks, checked judges
   │  pass
   ▼
Release ──► 3. Production feedback ── always on: traces, user signals, canaries
                 │  sampled traces
                 ▼
            2. Human review ── weekly: an expert labels failures
                 │
                 ├──► new failure modes become test items ──► back into 1
                 └──► fresh labels re-check the judges     ──► back into 1
```

**1. Automated (every change).** A golden set built from real traces and past failures, with **frozen
context**: the documents and tool responses are recorded, so a rerun sees the same world. Code checks run
first: output format, tool arguments, citations that exist, policy limits. Then one pass/fail LLM judge per
open-ended failure mode, validated against human labels on a **held-out split** (labels the judge's prompt
was never tuned on) before it can block anything. Compare the new version with the current one on the same
items, and gate on the error bar of the difference.

**2. Human review (on a cadence).** A domain expert reads a weekly sample of production traces, labels them,
and adds new failure modes. Those labels also re-check each judge's TPR and TNR. Anthropic's agent-evals
guide keeps systematic human studies "for calibrating LLM graders or evaluating subjective outputs where human
consensus serves as the reference standard"
([Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents), 2026-01-09).

**3. Production feedback (continuous).** Traces for every request. Cheap checks on every trace, and judges on
a sample. Explicit feedback (thumbs, complaints) and implicit signals (retries, escalations to a person,
customers coming back about the same issue). Canaries and A/B tests for big changes, sized so they can
actually detect the change.

**How they connect.** Every production failure becomes a golden-set item. Every human label sharpens a
judge. Every judge change is re-validated. Without the loop, the offline suite goes stale and stops predicting
production.

Say: "The loops matter more than any one of them. Production finds failures, people label them, and the
labels become tests and keep the judges honest."

### Follow one failure around the loops

| Where | What happens | What to say in the interview |
|---|---|---|
| Production | A customer gets a reply that cites a retired refund policy. A thumbs-down is logged with the trace. | "User signals point me to traces; they aren't the measurement." |
| Human review | In the weekly read, the expert labels it "stale policy cited" and finds 4 more like it. | "That's a new failure mode, with a count." |
| Automated | A code check is added: the cited policy must be the current version. The 5 traces become items. | "Code can check this one, so code does." |
| Next change | Every prompt or model change now runs those items. | "This failure can't come back silently." |
| Judge health | The same labels re-check the faithfulness judge: did it fail these replies? | "If the judge missed them, its TPR just dropped and I fix the judge." |

### How precise is any one score?

Every score from the automated loop is an estimate. At an 85% pass rate, the 95% error bar is **±9.9 points
on 50 items**, ±4.9 on 200, and ±2.2 on 1,000. Report the item count and the error bar with every score.

Also name the trade-off the account mentions. Automated evals are fast and cheap, but only as good as their
calibration (how well they've been checked against people). Human review is the reference, but slow. Online
data is real, but noisy and sparse.

## Small-team version

One engineer can run all three loops:

- **Level 1:** a CI job running the test set on every pull request.
- **Level 2:** a weekly hour of trace review with a domain expert.
- **Level 3:** the tracing and feature flags you already have. Self-hosted Langfuse or a hosted tracing tool
  covers the traces; the test set and the judges are yours to build.

**Cost:** a 200-item, 3-trial judged suite on a single-call feature is **about $13 per run** at list prices
fetched 2026-10-11 (the family walkthrough's arithmetic), plus about an hour a week of the expert's time.

**Time:** Hamel Husain and Shreya Shankar's evals FAQ says 60–80% of development time goes on error analysis
and evaluation ([FAQ](https://hamel.dev/blog/posts/evals-faq/), modified 2026-09-21), so plan for a large
share of your own time.

## Pitfalls

- **Listing BLEU, ROUGE or a generic "helpfulness" score as the evaluation.** These generic text-similarity
  and quality scores don't tell you whether your product's users got what they needed.
- **Judges never compared with human labels.** An unchecked judge is an untested test.
- **No path from production failures back into the test set.** The suite goes stale and keeps passing while
  users hit new failures.
