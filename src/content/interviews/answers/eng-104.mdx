## What they're really asking

> **If you only remember one thing, say this in the first minute:**
> "Yes. It triaged incoming support tickets: it read the ticket, looked up the customer's account and recent
> errors, and drafted a reply. Most of it was a fixed workflow; the model only chose which lookups to run. Its
> tools were read-only, and anything that changed data needed a human to approve it. Every run had a step cap, a
> dollar cap and a timeout. We scored it on 60 saved tickets after every prompt change, and the failure I learned
> most from was a loop that kept calling the same lookup."
>
> The rest of this page explains each part of that answer.

The interviewer is asking whether your agent experience is real and end to end, or a demo. They are checking
whether you have dealt with the parts that make agents hard in production: stop conditions, permissions,
evaluation and failure handling.

### What an agent is, and why it is harder than a normal service

A normal backend service runs the steps you wrote, in the order you wrote them. You know every database call it
can make before it runs.

An **agent** is different. A large language model (an **LLM**) decides the next step itself, in a loop: it
chooses a **tool** (a function you expose to it, such as "search tickets" or "look up account"), sees the result,
and decides again until it thinks the task is done. That means:

1. **You don't know the path in advance.** The model may call tools in an order you didn't expect, or call the
   same one ten times.
2. **Each step costs money and time.** Every step sends the whole conversation so far back to the model, so long
   runs get expensive quickly.
3. **A wrong step can have side effects.** If a tool can write (send an email, issue a refund), a model mistake
   becomes a real action.

So "end to end" means you handled those three things, not just that the loop ran. A single model call with a
system prompt is not an agent. A fixed sequence of model calls is a **workflow**, which is often the better
design.

## Answer

### If yes: the seven parts of "end to end"

The example is illustrative: a support-ticket triage agent. Replace it with your own.

```
New ticket arrives
   │  1. trigger
   ▼
Agent loop ───────────────────────────────────────────┐
   │  model reads ticket + results so far             │
   │  chooses next tool, or decides it is done        │
   ▼                                                  │
Tools                                                 │
   ├─ look up account (read-only) ────────────────────┤
   ├─ search recent errors (read-only) ───────────────┤
   └─ issue credit (write) ── needs human approval ───┘
   │
   │  stop when: done, or 10 steps, or $1, or timeout
   ▼
Draft reply + log of every step ──► human agent sends it
```

**The trigger** starts a run: here, a new ticket. **The loop** is the model choosing tools until it is done.
**The tools** are split into read-only (safe to run automatically) and write (gated by a human). **The stop
conditions** end runaway runs. **The log** records every step so you can debug and evaluate.

Cover the seven parts in this order:

| Part | What to cover | What to say in the interview |
|---|---|---|
| **1. Trigger and task** | What starts a run, and what a finished run produces | "A new ticket starts it. A finished run is a draft reply with the facts it looked up." |
| **2. Why an agent** | Why the model needed to choose steps, or an honest note that a fixed workflow did most of it | "Which lookups a ticket needs varies a lot, so the model chooses them. Everything else is fixed code." |
| **3. Tools and permissions** | Which tools, which were read-only, which needed human approval, how credentials were scoped | "Read tools run automatically. Issuing a credit needs a person to click approve. The agent's credentials can't write anywhere else." |
| **4. Stop conditions** | A step cap, a dollar or token cap, a wall-clock timeout, and what happens when one fires | "10 steps, $1, two minutes. When a cap fires, the ticket goes to a human with the log attached." |
| **5. State and recovery** | Where run state lived, whether a run could resume, how retries avoided repeating side effects | "Each step is saved. A retry skips steps that already wrote something." |
| **6. Evaluation** | A fixed task set, a task-level success rate (completed without human correction), rerun on every prompt or model change | "60 saved tickets with known good outcomes, rerun on every change." |
| **7. A failure** | A loop, a wrong tool call, an action that should have needed approval, and the fix | "It kept calling the same lookup with the same input. I added a check for repeated calls." |

### Why the cap matters: the cost of a run grows fast

Each step resends the whole conversation so far, and the conversation grows every step. So the cost of a run grows
faster than its number of steps. With an assumed start of 4,000 tokens (a **token** is a piece of text about ¾ of a
word), 1,500 tokens added per step and 10 steps, a run sends about **122,500 input tokens** in total. On Claude
Sonnet 5 that is about **$0.28** a run. A **$1 per-run cap** leaves room for a long run and still stops a loop.

Say it like this: "Each step resends the growing context, so ten steps cost about 22 times the first one, not
10 times. A one-dollar cap is generous for a normal run and stops a loop."

<details>
<summary>The arithmetic behind the numbers (for a Staff-level follow-up)</summary>

- Input tokens over N steps, starting context C0, Δ tokens added per step: N × C0 + Δ × N(N + 1) ÷ 2.
- N = 10, C0 = 4,000, Δ = 1,500 (all assumed): 40,000 + 1,500 × 55 = 40,000 + 82,500 = **122,500** input tokens.
- At $2 per million input tokens (Claude Sonnet 5, list prices fetched 2026-10-11): about **$0.25**. Plus about
  3,000 output tokens at $10 per million: about **$0.03**. Total about **$0.28**.
- The last step alone sends 4,000 + 1,500 × 10 = 19,000 tokens; the 10 steps together send 122,500, about 22×
  the first step's 4,000 + 1,500 = 5,500 (122,500 ÷ 5,500 ≈ 22.3).

</details>

Say so, and show what you have: a workflow with LLM steps you built, and the agent you would build next, with the
same seven parts as a plan. A clear plan with permissions and caps beats a vague claim.

## Small-team version

Most agents a small company ships are internal: triage, research, data entry, support drafting. The credible story
is usually:

- a workflow with one or two agentic steps;
- plain code instead of an agent framework;
- read-only tools by default, and a human approval for any write;
- a per-run cost cap;
- a regression set of 30 to 100 tasks, rerun on every change.

Saying you chose that over a fully autonomous agent, and why, is a strong answer. Know your cap's arithmetic from
the section above: about $0.28 for a ten-step run, so a $1 cap stops loops without stopping real work.

Say it like this: "It's mostly a workflow. The model only picks which lookups to run, it can't write without a
person, and every run stops at a dollar."

## Pitfalls

- **Calling a single chat call with a system prompt an agent.** The interviewer will ask what the model decided,
  and the answer is "nothing".
- **No stop conditions or cost cap.** One loop can burn through a month's budget overnight.
- **Tools with write access and no approval step.** A model mistake becomes a real action.
- **No task-level metric, only anecdotes.** Without a fixed task set, you can't tell whether a prompt change
  helped.
- **An agent where a workflow would do.** It adds cost and unpredictability for no gain.
