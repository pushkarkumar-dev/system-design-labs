## What they're really asking

> **If you only remember one thing, say this in the first minute:**
> "The brief was vague, so I wrote down who the user is and what decision the app helps with, picked the one flow
> that matters most, and built it end to end before anything else. I call the model API carefully: key from the
> environment, a timeout on every call, retries only for overload, a token limit, and a log line per call. I
> treat the model's reply as untrusted input and check it before using it. A small labelled set, run by one
> command, shows how well it works, and the README lists my assumptions and what I cut."
>
> The rest of this page explains each part of that answer.

The task, as reported: take an underspecified customer brief, decide what the customer probably needs, and ship
a small, well-behaved application on one vendor's model API in a few hours.

### What makes this different from a normal take-home

In a normal take-home the API you call is dependable. Here the API is a **large language model** (LLM): a service
that reads text and writes text. It costs money per call, it can be slow, it can be overloaded, and its replies
can be wrong or in the wrong format. "API hygiene" means handling all of that the way you would handle a flaky,
expensive, rate-limited third-party service. Treating its output as untrusted means checking it the way you check
user input.

### Words you need first

- **Tokens**: models read and write in pieces of words, roughly ¾ of an English word each. Providers price by the
  million tokens, and output costs more than input.
- **Prompt**: the text you send. The fixed instructions at the start are the **system prompt**.
- **`max_tokens`**: a request setting that caps how long the reply may be, which also caps its cost.
- **Prompt caching**: the provider remembers a prompt's opening part and bills it more cheaply when the next
  request starts with exactly the same text.
- **Eval** (evaluation): a set of inputs with known right answers, plus a script that runs the app on them and
  reports the score.

### Where it was reported

The only report is a vendor blog with no sources. It describes a 3–4 hour build and says reviewers grade
"shipped behavior, API hygiene" and "how you handled ambiguous requirements without asking the interviewer for
clarifications" <Cite id="s-2f725b952e" />. Treat that as low confidence, but those three signals are the ones
every take-home in this family rewards.

## Clarify first

If you can't ask, write the questions and your assumed answers at the top of the README:

- **Who is the user and what decision does the app help with?** Assume one persona and one job.
- **What data does it use?** Assume the brief's sample data only, treated as untrusted input.
- **Does it act or only answer?** Assume it only answers, or proposes actions a human confirms.
- **What does good look like?** Assume a labelled set of 20–30 inputs with expected behavior.
- **May you use Claude to write the code?** Anthropic's published guidance says of take-homes "Complete these

## Answer

### A picture of the app

```
User request
   │
   ▼
App code ── builds the prompt: system prompt + stable context first, then the request
   │
   ▼
API client ── key from env │ timeout │ max_tokens │ retry only on rate-limit/overload │ log line
   │
   ▼
Model API (the vendor)
   │  reply text (or structured output)
   ▼
Validate ── right shape? values allowed? if not → clear error or a human, never a guess
   │
   ▼
Answer to the user (or a proposed action the user confirms)
```

**App code.** It puts the system prompt and any context that never changes first, so prompt caching can apply.

**API client.** One small wrapper does all the hygiene, so every call gets it.

**Validate.** Checks the reply before anything uses it. If the app uses **tools** (functions the model may ask
your code to run), the program decides what each tool is allowed to do.

### Scope to one flow that works end to end

Pick the customer's most valuable request and build it fully before a second feature. Put the assumptions and the
cut list in the README. Say it like this: "One flow that works beats three that half work, and the README says
what I'd build next."

### API hygiene, concretely

- The key comes from the environment, never from code or logs.
- Every call has a timeout.
- Retries use **backoff** (waiting longer after each failure), and only for rate-limit and overload responses.
  Check the error codes in the API docs. Never retry a bad request; it will fail again.
- `max_tokens` fits the task.
- The system prompt and stable context go first, so prompt caching can apply.
- Use **structured output** or tool use (ways to ask the model for a given JSON shape) for anything the program
  parses, and still validate it.
- Log one line per call with the model, tokens and latency.

A cost estimate per request in the README shows you thought about money.

### Follow one request

An illustrative request through the app, with assumed token counts:

| Step | What happens | What to say in the interview |
|---|---|---|
| Build | The prompt is about 2,000 tokens: system prompt and the brief's sample data first, the user's question last. | "Stable text first, so repeat requests can be cached." |
| Call | The client reads the key from the environment, sets a timeout and `max_tokens` of 500. | "Every call gets the same hygiene from one wrapper." |
| Overload | The first attempt gets an overload response. The client waits and retries once. | "I retry overload, not bad requests." |
| Validate | The reply is checked against the expected shape. | "The model's reply is input, so I validate it." |
| Log | One line: model, 2,000 in, about 500 out, latency. | "That line is my cost and latency dashboard." |

That request costs about **0.9 cents** on Claude Sonnet 5 (arithmetic below).

### Treat output as untrusted

Validate shape and values. Route failures to a clear error or a human, not a crash or a guess. If the app uses
tools, the program enforces what each tool may do.

### Show it works

A small labelled set run by one command, with pass rates and the failures you read. Then a short section on what
you would do with another day: more cases; an **LLM judge** (a second model call that grades answers), checked
against your own labels; and **streaming** (sending the reply to the user piece by piece as it is written) for
long answers.

The family walkthrough has a runnable reference loop (model call, strict parsing, retry, human gate, eval) that
fits a 3–4 hour brief once you swap in the API call.

## Small-team version

This is what the first internal AI tool looks like: one flow, a managed API, a README a non-engineer can follow.
Build it in plain code, keep the eval in CI, and set a spend cap at the provider before anyone else gets the link.

**What it costs**, with assumed traffic: about **0.9 cents a request**, so 1,000 requests a day is **$9 a day,
about $270 per 30 days**, on Claude Sonnet 5 ($2 / $10 per 1M input / output tokens, fetched 2026-10-11).
Providers also set their own monthly spend limits per account tier, after which requests fail; check your tier's
current limit in the provider's docs before a launch. Revisit the design when a second team asks for the same thing.

<details>
<summary>The arithmetic behind the numbers (for a Staff-level follow-up)</summary>

- Assumed: 2,000 input and 500 output tokens per request.
- 2,000 × $2 per million = $0.004; 500 × $10 per million = $0.005; total **$0.009**.
- × 1,000 requests = $9 a day; × 30 = **$270**.

## Pitfalls

- **Three half-features.** Building one for every reading of the brief leaves nothing finished to show.
- **Retrying every error.** Retrying invalid requests just repeats the failure until the rate limit trips.
- **No written assumptions.** The reviewer can't tell your judgment from an accident.
- **Ignoring the take-home's AI-tool instructions.** Using a coding assistant where it is not allowed can end the
  process.
