## What they're really asking

> **If you only remember one thing, say this in the first minute:**
> "My view is that AI is good at well-specified changes in code with strong tests, and at explaining code I
> haven't seen. It fails where correctness depends on things it can't see, and it is confidently wrong when it
> fails. So the scarce skill is checking its work. That's how I use it every day: a coding agent for bug fixes,
> with a plan I approve and a diff I read, and no AI near customer data."
>
> The rest of this page explains each part of that answer, so you can say it with your own examples.

The interviewer wants to know whether you have a considered, engineer's view of AI, grounded in how you
actually use it.

This question has two halves, and they check each other. A big view of AI with thin daily use sounds like
reading articles. Heavy daily use with no view sounds like habit. A good answer joins them: your view should
come from what you have seen the tool do, and your daily use should follow from your view.

It is different from a normal "tell me about yourself" question in one way. The topic is a tool whose output is
often wrong in convincing ways, and that almost every engineer now claims to use. So the interviewer is not
impressed by enthusiasm. They listen for specifics: where it works, where it fails, and how you check it.

The title is a PracHub listing (PracHub collects reported interview questions) for Microsoft software engineers,
dated 2026-09-30, with no round stated (<Cite id="s-d302bba651" />). Treat it as a behavioral or
hiring-manager question.

### Words you need first

- A **large language model (LLM)** is a program trained on a huge amount of text and code that predicts what
  text should come next. Chat and coding tools are built on one.
- A **coding agent** is an AI tool that does more than suggest code. It reads files, edits several of them, runs
  tests, and keeps going until it thinks the task is done.
- A **hallucination** is a confident answer that is false, such as a function that doesn't exist.

## Clarify first

- **Which view?** "Do you want my view of AI in software engineering, or AI in general?" Usually the first;
  offer to add a sentence about the second.
- **Which tools?** "Should I talk about tools my current employer approves, or personal projects too?" Both, if
  you're clear which is which.
- **Their tools.** Ask whether the team uses specific tools. Tailoring the daily-use half helps.

## Answer

### The example we will follow

This page follows one illustrative engineer, Sam: a backend engineer on an orders service written in Go, who has
used one coding agent daily for about six months. Once, the agent wrote a database migration that passed every
test but would have locked a large table; staging caught it. Use the shape, with your own facts.

### Your view, in three sentences

Say what AI is good at in engineering today, where it fails, and what you think follows. Make it specific
enough that someone could disagree with it. Here is the shape (fill in your own):

| Sentence | Sam's version (illustrative) | Where it comes from |
|---|---|---|
| **Good at** | "It's good at well-specified changes in code with strong tests, and at explaining unfamiliar code." | Six months of bug fixes |
| **Fails at** | "It fails where correctness depends on context it can't see, like the size of a production table, and it's confidently wrong when it does." | The migration near miss |
| **So what** | "The scarce skill is verification." | Both of the above |

Each sentence points at a story you can tell if asked. That is what makes it an engineer's view rather than a
keynote.

The [AI-native guide](/system-design-labs/interviews/ai-native/) argues the same point from published
evidence. One study worth knowing: in an Anthropic trial with 52 mostly junior engineers, the group using AI
scored 50% on a follow-up quiz against 67% for the group without it, with the biggest gap on debugging
([Anthropic research, 2026-01-29](https://www.anthropic.com/research/AI-assistance-coding-skills)). It is a
good basis for saying how you keep your own skills sharp. Say it like this: "When something breaks, I debug it
myself first. Otherwise I'd stop learning the system I'm responsible for."

### Your daily use, in four beats

Give the four beats in about two minutes:

1. **Workflows.** Two or three, named concretely: what you hand the tool and what comes back. Sam: "For bug
   fixes I give the agent the failing test and the package, and approve its plan before it writes code."
2. **Checks.** How you verify each. Sam: "I read the whole diff and run the race detector."
3. **A failure** you caught. Sam: "It once wrote a migration that passed our tests and would have locked our
   biggest table. Staging caught it."
4. **Limits.** Where you don't use it, and why. Sam: "I write migrations myself now, and customer data never
   goes into external tools."

The loop behind those beats is a small system:

```
Task (failing test)
   │
   ▼
Agent's plan ── you approve or correct it
   │
   ▼
Agent edits code and runs the tests
   │
   ▼
Your review ── full diff, race detector, staging
   │  a mistake got through, or nearly did?
   ▼
Rule file / CI check ── so it is caught next time
```

Each step on the way is a place where you add judgment: a checkable task, an approved plan, a real review, and a
**rule file** (a text file the agent reads at the start of every task) that grows with each mistake.

### An outcome, measured honestly

End with what changed, not how much you use it. Large employers increasingly review engineers on AI impact
rather than usage. Meta reportedly judges how employees use AI to "Enhance individual productivity", "Build
tools that actively improve team performance" and "Contribute to Meta's wider AI transformation efforts"
([Storyboard18, 2025-11-17](https://www.storyboard18.com/digital/meta-may-lower-appraisals-for-employees-who-dont-use-ai-enough-84313.htm)).

Use the same three levels in your answer:

| Level | Question it answers | Sam's version (illustrative) |
|---|---|---|
| **You** | What do you do? | Daily bug fixes with a plan and a full diff review |
| **Your team** | What did you build for others? | A lock-duration check in CI for every migration |
| **Your organization** | How did you change practice? | Proposed plan approval as the team default |

If you haven't measured a speed-up, don't invent one. Say: "I haven't measured my speed-up properly, so I won't
give you a percentage. The CI check is the outcome I'm proudest of, because it protects everyone."

In plain words: the Senior answer stays at the "you" level of the table above. The Staff answer reaches the team
and organization levels, and includes something you decided to stop doing.

## Small-team version

A small company's first AI hire will set the team's norms. Say what you would set up in the first month:

- **Approved tools per kind of data**: which tools may see source code, which may see customer data (often none).
- **A review rule** for agent-written changes.
- **A shared rule file** that grows with each agent mistake.
- **A spend cap.** Agents on a provider's API are billed by the **token**, a chunk of text of roughly ¾ of a word.
  On the family walkthrough's assumed usage, an API-billed coding agent costs about **$69 per engineer a month**,
  so ten engineers is about **$690**. A cap set at two or three times that catches a runaway loop without
  blocking normal work.

<details>
<summary>The arithmetic behind the numbers (for a Staff-level follow-up)</summary>

- **Assumed use per engineer per day:** 2M input tokens, 1.6M of them **cache reads** (repeated text the provider
  bills at a lower price), and 0.2M output tokens.
- **Claude Sonnet 5 list prices, fetched 2026-10-11:** $2 per million input, $0.20 per million cached input, $10
  per million output.
- **Per day:** 0.4M × $2 + 1.6M × $0.20 + 0.2M × $10 = $0.80 + $0.32 + $2.00 = $3.12.
- **Per month:** $3.12 × 22 working days ≈ $69. Ten engineers ≈ $690. A cap at 2–3× is about $1,400–$2,100 a
  month for the team.

</details>

Also say which uses you would discourage, and why. Say it like this: "I'd make the safe path the easy one: one
approved tool, clear data rules, and a check in CI for every mistake we've already made once."

## Pitfalls

- **A keynote about the future with no workflows.** It sounds like you read about AI rather than use it.
- **"I use it for everything."** It suggests you don't decide where it fits, which is the judgment they want.
- **A productivity number you haven't measured.** People's sense of their own speed-up is unreliable, so an
  invented number costs credibility.
- **No mention of where AI fails.** A view without failure modes is enthusiasm, not a view.
