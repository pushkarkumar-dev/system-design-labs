## What they're really asking

> **If you only remember one thing, say this in the first minute:**
> "I'd start with a threat model: who uses the product, including teenagers and people in crisis, what they could
> make it do, and what content comes in from outside. Then I'd add layers, because no single check catches
> everything: product limits, input and output checks, the model's own rules, and no actions without the user
> confirming. I'd measure each harm with its own test set, and also measure how often we wrongly refuse. And I'd
> run it like any production system: sampling real outputs, an on-call path, and a kill switch."
>
> The rest of this page explains each part of that answer, so you can say it with understanding.

The question is: how do you approach safety for **generative AI (GenAI)** in a consumer product? GenAI means
models that produce text, images or other content. The interviewer wants to know whether you can turn "safety"
into an operating plan: a threat model, layered controls, measurement and an incident process, with the trade-offs
stated.

### What makes this different from normal product safety

You already know how to secure a web product: authentication, input validation, rate limits, audit logs. Most of
that carries over. Three things are new.

1. **The output is not fixed.** A **large language model (LLM)** is a program that reads text and writes text. The
   same question can get two different answers. You can't list every bad output in advance and block it.
2. **Text can carry instructions.** If the product reads an uploaded file, a web page or an email, an attacker can
   hide instructions in it, and the model may follow them. This is called **prompt injection**. It is like SQL
   injection, except there is no parameterized-query fix.
3. **The harm is often in what the product says.** Dangerous advice or a confident wrong answer is not an error in
   your logs. The company is still responsible for it.

So the answer is a set of layers plus measurement, not one filter.

The question is on an aggregator list tagged OpenAI, Anthropic and Google, with no detail about the round
(<Cite id="s-d7a8e88bf0" />). Expect the interviewer to pick a concrete product and push on specifics. Stay out of
principles-only territory: Hello Interview's OpenAI guide warns against "a rehearsed speech about AGI"
(<Cite id="s-4d55d9b987" />), meaning artificial general intelligence.

## Clarify first

The harms depend heavily on the product, so ask:

- "Which product? A chat assistant, image generation, an agent that takes actions?" The harms differ a lot.
- "Who are the users? Are minors possible?"
- "Is there a trust-and-safety team, or am I it?" This changes what you build versus buy.
- "What can the system do beyond producing text: browse, call tools, write to accounts?"

For the rest of this page, assume the answers are: a chat assistant inside a consumer app, users may be under 18,
users can upload files, the assistant can save notes to the user's account, and you are the safety owner.

## Answer

### 1. Threat model first

A **threat model** is a list of who might cause harm, how, and to whom. For our assistant:

- **Who uses it:** adults, teenagers, and some people in crisis.
- **What they might try:** get dangerous instructions, harass someone, extract other users' data.
- **What enters from outside:** uploaded files, which can carry prompt injection.
- **What it can do in the world:** save notes to the account.

Then list the harms: dangerous advice, harassment or sexual content, self-harm, privacy leaks, impersonation,
fraud, **over-reliance** (users trusting a wrong answer), and actions taken on injected instructions.

### 2. Layered controls

Picture the path of one message through the product:

```
User message (+ uploaded file)
   │
   ▼
Product limits ── rate limits, age checks, which features this user can reach
   │
   ▼
Input check ── a classifier flags harmful requests and hidden instructions
   │
   ▼
Model + system prompt ── chosen model, your product's own rules
   │
   ▼
Output check ── a classifier flags harmful replies before the user sees them
   │
   ▼
Action limits ── "save note" only after the user confirms
   │
   ▼
User ── sees an AI label, a "report this" button, crisis resources where relevant
```

**Product limits** are ordinary code, so they come first and cost almost nothing. A **classifier** is a smaller
model that labels text by category (for example "self-harm"); a provider's **moderation endpoint** is an API that
does this for you. The **system prompt** is the instructions your product puts in front of every conversation, and
the model choice sets the rules the vendor trained in. **Action limits** stop an injected instruction from doing
damage on its own. The last box is about **disclosure** and **human paths**: users know it is AI and what it
can't do, and can reach a person or crisis resources.

In short:

- **Model and system prompt:** choose a model whose policies fit; write the product's own rules.
- **Input and output checks:** classifiers or moderation endpoints per harm area.
- **Product limits:** rate limits, no autonomous writes without confirmation, scoped credentials for any tool.
- **Human paths:** escalation to a person, crisis resources where relevant, in-product reporting.
- **Disclosure:** users know it's AI and what it can't do.

### 3. Measurement

You test an AI feature with an **eval**: a fixed set of test inputs plus a scoring rule, run against every model or
prompt version. Think of a regression suite whose results are percentages. Build one eval set per harm area,
refreshed from real reports and from **red-team** findings (people deliberately trying to make the model
misbehave).

Measure the other side too. **Over-refusal** is the model refusing a legitimate request because it looks a bit like
a harmful one. It is the AI version of a false positive. Compare every model or prompt change with the previous
version before release, on both harm and over-refusal.

Say it like this: "If I only measure harm, the safest model is one that refuses everything. So I track wrong
refusals on real, legitimate questions next to harmful completions, with a threshold for each."

### 4. Operations

Production sampling, an on-call path for safety incidents, a **kill switch** per feature (a flag that turns it
off), and a written incident review.

Evals miss things, and the best-known case shows how. OpenAI's April 2025 GPT-4o update was rolled back for
**sycophancy**: the model told users what they wanted to hear. Per a brief quoting OpenAI's postmortem, there were
no deployment evals tracking sycophancy, and expert testers' "felt slightly off" was overridden by positive user
signals ([Georgetown Law brief](https://www.law.georgetown.edu/tech-institute/insights/tech-brief-ai-sycophancy-openai/), postmortem 2025-05-02).
The lesson for operations: a credible report that no eval explains is a reason to stop, even when users seem happy.

### 5. Trade-offs

Every layer costs latency, money or usefulness. An output check adds a call before the user sees anything. A
strict input check refuses some honest students. Say which you accept for this product and why.

Say it like this: "For an app teenagers use, I'd accept more wrong refusals on borderline topics, and I'd tell the
team that's a choice we made, not a bug."

In plain terms: Senior designs the layers well. Staff also decides who has authority, what overrides the metrics,
and when the company has outgrown "the AI owner does safety".

## Small-team version

With no trust-and-safety team, buy the moderation layer: provider safety features or a classifier service, after
checking what each one covers. Build the parts only you can: the threat model for your product, per-harm evals
from your own traffic, a kill switch, and a weekly read of real outputs.

The build side is cheap in money:

- A 200-item per-harm suite, run 3 times on a feature that makes one model call, is about **$13 per run** at Claude
  Sonnet 5 list prices fetched 2026-10-11 (the eval-system walkthrough's arithmetic). Model prices are per
  **token**, a chunk of text of roughly ¾ of a word.
- Reading 50 outputs a week at an assumed 2 minutes each is about **1.7 hours** of an engineer's time.

You own what the product says. A tribunal held Air Canada responsible for its chatbot's advice
([Law360 Canada, 2024-02](https://www.law360.ca/ca/articles/1804075)). Revisit the setup when you serve minors,
reach consumer scale, or enter a regulated domain.

## Pitfalls

- **Principles with no gates, owners or numbers.** "We take safety seriously" can't block a launch.
- **Treating the model vendor's safety layer as complete.** It doesn't know your users or your domain's harms.
- **Ignoring prompt injection through user-supplied content.** Every uploaded file is a possible instruction.
- **Measuring harm but not over-refusal.** You end up shipping a product that refuses its own users.
