## What they're really asking

> **If you only remember one thing, say this in the first minute:**
> "I'll design the solution out loud first, then split the work. The assistant drafts the parts I can check in
> under a minute: boilerplate classes, test tables, a printer. I keep the parts that need judgment: the
> algorithm, the interfaces and the edge cases. I'll paste in small pieces, run the tests after each one, and
> review the tricky lines myself."
>
> The rest of this page explains each part of that answer.

The question behind this report is: can you use the assistant *enough*?

Most advice about AI coding rounds warns you not to trust the assistant. This report is the counterweight. The
assistant is a chat tool backed by a **large language model (LLM)**, a program trained on huge amounts of text
and code that writes a plausible reply to what you type. At a company that expects you to use it, typing
everything yourself is graded as poor judgment about your tools, in the same way that hand-writing a JSON parser
would be in a normal round.

So the signal is **calibration**: knowing which work to hand over and which to keep. Hand over what you can check
quickly. Keep what needs your judgment.

A Meta machine-learning engineer candidate had two AI-assisted coding rounds, a card game and a "maximum unique
characters" problem. After the rejection, the recruiter's feedback was "less manual work, more on AI"
(<Cite id="s-443984bc07" />).

## Clarify first

- **The card game.** Which rules are fixed and which are configurable? What do the tests call (class names,
  method signatures)?
- **"Maximum unique characters".** Ask for the exact definition. Longest substring with all distinct
  characters? A window of fixed size with the most distinct characters? Ask for one example input and output.
- **The character set.** Lowercase letters only, or any Unicode? That decides between a 26-slot array and a map.
- **How the interviewer wants AI used.** Whole functions, or review and tests only? Reports vary by interviewer
  (<Cite id="s-27f34bf219" />), so ask: "Would you like me to have the assistant draft code, or use it mostly
  for review and tests?"

## Answer

### Plan out loud, then split the work

Say the design in a minute, then say which parts go to the assistant. Here is the split for both problems:

| Piece | Who | Why |
|---|---|---|
| Card game: class layout and the rules engine's interface | you | the interface is the design; everything else plugs into it |
| `Card`, `Deck`, shuffle boilerplate, test fixtures, a printer | assistant | quick to check, slow to type |
| String problem: the algorithm (a sliding window, below) | you | this is what the round grades |
| The window code and its edge-case tests | assistant drafts, you review | the tricky line is easy to spot once you know it |

### Words you need first

- **Sliding window**: two positions, `left` and `right`, mark the current stretch of the string. Move `right`
  forward one character at a time. When the new character breaks the rule (here: it repeats), move `left`
  forward until the rule holds again. Each character enters and leaves once, so it is O(n).
- **Last-seen index**: for each character, the position where it last appeared. It lets `left` jump straight
  past the earlier copy instead of stepping one by one.
- **Fisher–Yates shuffle**: the standard fair shuffle. Walk from the last card down; swap each card with a random
  card at or before it.

### The worked example: one line decides the string problem

Assume the interviewer confirms "longest substring with no repeated character". The assistant's draft will
usually be right on the textbook input and can still be wrong. Walk it through two inputs:

| Input | Right answer | A draft with `left = lastSeen[c] + 1` | A draft with `left = max(left, lastSeen[c] + 1)` |
|---|---|---|---|
| `abcabcbb` | 3 (`abc`) | 3 | 3 |
| `abba` | 2 (`ab` or `ba`) | **3** (wrong) | 2 |

Why `abba` breaks the first draft: at the second `b`, `left` jumps to position 2. At the final `a`, the last `a`
was at position 0, so the first draft moves `left` back to 1, and the window `bba` (length 3) is counted even
though it repeats `b`. The `max` keeps `left` from ever moving backwards.

Say it like this: "The left edge must never move backwards. `abba` is my test for that."

That is the whole review of the string problem: one line, one four-letter test. The assistant typed it in
seconds; you checked it in seconds. That is the delegation the feedback asked for.

### Delegate in checkable pieces

Each request should produce something you can review in under a minute: one class, one function, one table of
test cases. Paste, run, move on. Hand-typing a 40-line deck class while the assistant sits idle is the pattern
the recruiter's feedback describes.

### Keep the judgment on the card game too

Check shuffle fairness. Fisher–Yates swaps each position with a random index in the *remaining* range. Swapping
with a random index across the whole deck looks almost the same and is a well-known biased version. Then check
the turn and end-of-game rules against the spec, line by line. Those rules are where a draft quietly invents
behavior the spec didn't ask for.

### Show the evidence

Run the tests after each paste and say what passed. If there is time, ask the assistant for **property tests**,
tests that check a rule over many generated inputs instead of one example. For the string problem: the result is
never more than the number of distinct characters in the input, and never more than the input's length.

## Small-team version

The same miscalibration costs real time and money at work, in both directions:

- **Under-use.** An engineer who types everything doesn't get the speed-up the team pays for. The seat is cheap
  (the family walkthrough works out about $150 a month for a heavy user under stated assumptions); the engineer's
  hours are not.
- **Over-use.** An engineer who pastes everything ships bugs like the `abba` one, and someone pays for them later
  in an incident.
- **A useful team norm.** The agent (an assistant that can edit files and run commands) drafts anything a
  reviewer can check in seconds: scaffolding, fixtures, migrations with tests, glue code. A person owns
  interfaces, invariants and the test cases.
- **Revisit the split when review queues grow.** A growing queue usually means the pieces are too large, not that
  the agent should do less.

## Pitfalls

- **Writing all the code by hand at a company that expects AI use.** The reported feedback was "less manual
  work".
- **Swinging the other way and pasting a whole solution.** If you can't explain it, it doesn't count.
- **Not clarifying an ambiguous name like "maximum unique characters".** Two reasonable readings give two
  different algorithms.
- **Skipping tests because the code "looks right".** The `abba` bug looks right.
